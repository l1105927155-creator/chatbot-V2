## 待整改 / 待验证

### P2 — 复核群聊 Agent 的**全部可执行入口**（优先）

观察：群聊 `bash` 走 `group-scope-runner.py`：Bubblewrap 隔离挂载和网络、cgroup 内存/任务/CPU 限额、作用域与来源逐调用校验。与此同时，群聊 DSH 的**主进程**仍由宿主启动；隔离明确建立在受控 Shell 子进程上，而非把完整 Agent 进程置于同一命名空间中。

因此“群聊 Bash 已隔离”不自动证明“群聊的所有工具及原生扩展入口均已隔离”。这是一项**隔离面覆盖风险**，目前没有基于所查代码发现可利用的实际逃逸路径，不应将其表述为已证实的漏洞。

整改与验收：
- 枚举群聊 Profile 在实际 ACP 请求中暴露的全部工具，包括 Skill、web、MCP、子进程 provider 及未来插件的间接执行入口。
- 用真实执行证据分别检查工作目录、文件读取/写入、环境变量、主机凭据、网络访问、输出落盘、工具调用来源及副作用路径；明确哪些属于宿主有意提供的**受控服务**（如受限网页搜索），哪些必须留在群聊执行沙箱。
- 增加至少一个否定案例：试图通过非 Bash 工具或间接入口访问主机敏感路径 / Owner 数据，不得成功；更新工具组合时保留该回归门。
- 先复用当前原生 Guard/Provider/MCP 限制，**不为这项审计另建统一权限平台或容器体系**。

### P2 — 按群工作区的总体容量与生命周期策略

观察：`group_volume.py` 以平台 / Bot / 群 ID 派生独立空间，每群固定 1 GiB，并验证卷与预留。该实现解决单群写满，但不能自动保证**多群累计占用**受产品预算约束。

整改与验收：
- 在新增准入群/首次创建群卷前，检查宿主可用空间与整体预留额度；明确超预算时**拒绝新增**而非降低沙箱硬配额或挪用其他群卷。
- 明确取消群准入后，沙箱数据是保留、归档还是经用户确认后清除；禁止未经决定自动删除可能有用的群数据。
- 测试多群连续创建、空间不足和失败回滚，确保已有群与生产服务不受影响。
- 当前仅一个主测试群，这项不必阻断已批准的单群安全测试，但扩大群准入之前必须定案。

### P3 — Owner 主机执行与“完整 DSH”之间的剩余差异

观察：Owner 已拥有主机 FS、Shell 和一般网络能力，但当前 `tool-bash` 仍禁后台运行，单次命令默认 120 秒、最长 600 秒。因此这是“主机范围内的 DSH 原生工具能力”，**并非所有 DSH 可用执行模式均已开放**。

建议：保留这一差异作为显式产品边界，正常主机任务实测若因超时/后台需求无法完成，再根据具体故事评审。不要为了追求“无限制”自动开放后台进程、root 或任意权限提升。
