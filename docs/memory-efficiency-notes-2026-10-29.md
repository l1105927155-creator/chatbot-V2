# 记忆整理效率：诊断与候选方向

用户询问消息积压是否过大及成熟方案；本轮先完成进度/超时，不把效率建议默认为修改语义、频率或迁移框架的授权。

当次范围34442→36486在697823265实际包含1362条Journal消息，成功提交400条到34965，剩962条。条数包含整理来源中的Bot消息，与每日99条群友触发门槛不同。每批100条，并带入相关/高显著性旧记忆；实际完整请求约87–106KB。问题是第五批触发本层120秒等待，不是“达到400条容量上限”。规模应按消息长度、旧记忆输入、单批耗时、增量产生速度与处理速度评估，不能按一个固定条数宣称安全。

查阅的主要官方材料：

- [Mem0算法说明](https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm)：当前新增提炼走single-pass ADD-only，避免每次立即做更新/删除比较；实体关联和异步处理支持其检索。其性能数字包含托管平台专有优化，不可承诺本项目同样收益。
- [Mem0新增API源码文档](https://github.com/mem0ai/mem0/blob/main/docs/api-reference/memory/add-memories.mdx)：异步新增返回event_id，可查询结果。
- [Letta memory/dreaming文档](https://docs.letta.com/configuration/memory)：背景复盘近期对话、整理记忆，以事件/步骤触发，避免集中阻塞正在进行的对话。

结合本项目的候选顺序：

1. 用现有AstrBot任务机制更及时消化增量，让`/new`只做必要尾段；保留失败阻止重置、不自动重试的约定。具体频率与条件另定，不能静默改Owner当前22点设置。
2. 减少每批无关旧记忆：优先按参与者/话题缩小候选，避免每批都重复带入大量高权重但无关的旧记忆。显著性不应被误用为每次都读的理由。
3. 区分便宜的增量形成与较重的跨批整合/强化/遗忘，但仍允许人格与语境影响理解；不能直接把Mem0 ADD-only照搬成取消修订和遗忘。
4. 在合成大积压上衡量总输入/输出、每批时延、提交速度和长期召回；若做受控并行，必须解决同一记忆并发修订及时间/说话者归属，不能靠无序并发写库换速度。

以上是结合资料与当前代码的设计推论，尚未实施，也不能据官方基准推断本群实际性能。原始Journal继续作为完整来源，不为提速丢弃消息或猜测事实置信度。
