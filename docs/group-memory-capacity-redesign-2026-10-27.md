# 群记忆容量与增量分批重做

## 问题与目标

用户要求重新处理容量设计。原实现按100条读取消息，整批加入最多80条既有记忆，超过固定输入大小直接失败；记忆层另设输出token上限及64KiB字符上限。4096改为16384只能缓解样本，无法形成容量契约。

目标是让单次整理范围受控、积压可连续推进，清楚区分原生模型限制、输入预检估计和传输安全限额。仍保持失败不自动重试，失败批次不提交；已经提交的批次保留。99条仍是每日任务触发门槛，不是整理容量单位。

## 实现

- 私有记忆socket增加零生成的capacity查询，读取当前精确路由的原生 `llm.resolveModelInfo`。移除记忆层全部maxTokens覆盖，生成沿用DSH模型路由配置。
- native `contextWindow` 是请求与响应合计窗口，`defaultMaxTokens` 是路由配置的输出默认上限。缺失/无效容量明确失败，不另填4096/16384等数字。**元数据来自适配器配置或catalog，可能包含框架默认，不能称厂商硬上限。** 当前wb原生报告262144/128000；其中上下文来自PiAi的框架默认，未验证为服务商实际容量。
- 新 `batching.py` 按完整序列化请求的UTF-8字节估计输入开销；预检范围取原生窗口减原生输出预留。同时计算完整socket请求，包含JSON转义、身份、固定长度token及预期容量。字节估计不是精确tokenizer，不能保证服务商一定接受。
- Journal页面仍最多100条，但每次仅选可容纳的连续完整前缀。不给超长消息截正文、跳过或假推进；首条无法容纳时明确 `MEMORY_MESSAGE_TOO_LARGE` 并保留Journal定位。指南/人格超限也明确失败。本轮不增加单条跨批分片状态。
- 既有记忆按相关度与显著性排序，首条新消息可放入后优先给一条可容纳的旧记忆位置，再扩展连续消息及剩余旧记忆。整条选入；未提供的旧记忆不删除、不允许模型引用或改写。记录选中/候选数量及输入大小，不记录原文。
- 用预期容量核对发起时的原生准备结果。热改容量不匹配时明确失败，不重试；原生prepareCall绑定adapter registration后发起。
- 去掉64KiB字符限制。私有socket请求1MiB、响应4MiB是明确的宿主内存/传输安全限制，不是模型输出token预算；响应按UTF-8字节和最终JSON封包校验。模型输出耗尽、协议超限、超时、上下文拒绝分别记录安全类别，不记录提供方原始错误文本。

### 2026-11-02 订阅模型容量兼容

固定版DSH的`LlmResolvedModelInfo`只公开`contextWindow`和调用默认值`defaultMaxTokens`，不公开模型描述符的`maxTokens`。已认证订阅目录中的`maxTokens`是该模型声明的输出上限，但订阅适配器没有把它设为普通聊天调用默认值；因此Terra的原生解析会有上下文窗口、没有`defaultMaxTokens`，按原合同会被批处理拒绝为容量未知。

订阅适配器现在通过Cordis服务`v2SubscriptionMemoryCapacity`仅向记忆整理暴露当前账户范围内精确模型描述符的`maxTokens`。记忆整理只在标准默认值缺失时采用该目录输出上限，并把它显式传给该次记忆`prepareCall`；随后核对准备结果的上下文窗口和实际输出`maxTokens`。普通聊天仍不设置`maxTokens`默认值。未知或无效的目录输出上限仍失败关闭，目录变化仍以`MEMORY_CAPACITY_CHANGED`拒绝提交。

## 对照外部实现

[Letta memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks) 对常驻记忆块设容量限制，[Zep Memory API](https://help.getzep.com/v2/memory) 推荐逐轮添加并检索相关上下文。它们支持“增量写入、有限工作集”的方向，不能用文档推导任意输入都不会失败，也没有因此迁移它们的记忆语义、置信度或架构。
