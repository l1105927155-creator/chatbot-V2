# Mem0 隔离接入评估（2026-10-29）

本轮是可复用性试验，未接入生产、未迁移或清空既有记忆，未重放任何真实群消息。结论是：Mem0 能承担提炼、向量存储和检索，但不是当前群记忆系统的直接替代品。它省下的是通用记忆基础设施；归属、来源、完整提交与 `/new` 成功判定仍需集成层负责。自动整理的修订、显著性维护与遗忘也不能由当前 ADD-only 提炼直接替代。

## 可复现范围

- 脚本：`scripts/evaluate-mem0.py`；独立环境锁定 `scripts/fixtures/mem0-eval-requirements.txt`，核心为 `mem0ai==2.2.1`、`fastembed==0.9.1`、`qdrant-client==1.20.0`。没有改生产 Python 环境或 `upstream.lock.json`。
- 三组：Mem0 默认提炼、Mem0 加中文归属/主观理解/来源指南、当前 V2 的 planner → 原生模型 → 来源 ID 校验 → MemoryStore 提交流程。V2 不是完整 AstrBot `/new` 集成测试。
- 同一原生 DSH 路由 `wb/deepseek-v4.1-flash`，真实模型调用，无工具或认知 Session。Mem0 的 LLM 对象在测试夹具中替换为原生适配器；没有改它的提炼、存储或检索源码。
- 使用真实本地中文 embedding `BAAI/bge-small-zh-v1.5`（512维），不是随机/哈希向量。Mem0 的可选 spaCy NLP extras 未安装，日志明确报告相应词形/实体识别降级；不据此评判完整 NLP 配置的效果。首次还下载了库自身所需的模型资源，因此冷启动时间不是纯推理时间。
- 输入共108条合成消息，分5批：A自述与B反驳、A自我更正、长期维护与临时约定、再次维护与取消约定、99条轻量闲聊加1条维护经历。每组相同输入顺序。另测原消息重放、另一群暗号的过滤检索，以及独立故障注入。
- Mem0 默认系统提示为33,653字符，超过当前原生记忆接口的32,000字符传输限制。仅在隔离目录复制适配器，将该单项字符检查改为64,000；没有调大输出 token 配置或更改生产接口。
- `MEM0_TELEMETRY=False`；数据库、原消息缓存和生成 socket 位于隔离目录。模型资源下载仅用于本地 embedding，真实模型仅使用现有配置的提供方，输入为合成数据。

复现命令（连接配置含密钥，沿用既有私有模型夹具格式，不能提交或公开）：

```bash
uv venv .runtime/mem0-eval/.venv --python 3.12
uv pip install --python .runtime/mem0-eval/.venv/bin/python -r scripts/fixtures/mem0-eval-requirements.txt
HF_HUB_DISABLE_XET=1 .runtime/mem0-eval/.venv/bin/python scripts/evaluate-mem0.py \
  --output .runtime/mem0-eval/run-01 \
  --connection /absolute/private/connection.json --workers 1
```

连接配置为 `{key, providers}`，其中 `providers` 是固定 DSH PiAi 的提供方配置，引用环境变量 `WB_API_KEY`。`--output` 必须是不存在的新目录。脚本结束会关闭自建原生适配器，不操作运行中的 Bot 服务。

## 实际观察

| 能力 | 观察与边界 |
| --- | --- |
| 第三人反驳 | 三组样本均保留A的自述与B的反驳，没有把B的话直接写成A的事实。Mem0默认生成英文，加指南后中文并在正文标来源。不能据单例保证所有人格/上下文。 |
| A后来自己更正 | Mem0新增更正条目，保留旧自述；V2修订原条目并保留来源演变。新增记录也能表达更正，但检索和后续回答需要正确理解新旧关系。 |
| Bot主观感受 | 加指南的Mem0记录了Bot因长期维护而安心；默认组漏掉该感受。指南可以调整取舍，不能由此认定整个产品语义与默认提示完全一致。 |
| 长期维护经历 | 两种引擎均保留本次维护经历；V2合并并保留显著性，Mem0继续新增经历。没有真实跨周试验，未验证长期淡忘/强化效果。 |
| 取消临时安排 | Mem0新增取消说明，原约定仍可作为独立条目检索。V2修订原条目为“原约定，后来取消”。不能把Mem0并存理解为必然错误回答；但它不等于自动归档、合并或遗忘。 |
| 原文来源 | Mem0每条metadata保存调用方传入的整批ID；具体来源可写正文，但没有逐条结构化校验。其最近消息缓存只保留10条，不能替代canonical Journal。 |
| 群隔离 | 使用完整群namespace的filters后，A群搜索没有返回B群暗号，B群可以找到。只是过滤样本，不是权限、跨群ID攻击、宿主访问的完整验收。 |
| 重放 | 首轮两种Mem0配置重放同一条来源后条目数不变。语义近重复、移出top10后的重放、并发和全库幂等未验证，不能把检索内去重当作全局幂等保证。 |
| 解析失败 | 两组均复现：注入非JSON模型输出后，日志报解析错误，但add正常返回 `{"results":[]}`。合法“无可记内容”与该失败在返回值上不可区分。 |
| 部分写入失败 | 顺序轮中两组均复现：模拟2条记忆的批量写失败、逐条补写只成功1条，add正常返回这1条，没有整批失败标记。不能以正常返回直接推进整批Journal游标。 |

另外只读核查2.2.1源码：自动add主要是一次提炼、检索top10旧记忆、批量embedding与新增，既有记忆的直接CRUD API仍存在；不要把“自动提炼只新增”表述成“库不能更新/删除”。本版提炼返回的 `linked_memory_ids` 没有随记录持久化，实体索引的同名字段是另一套关联；不能假定模型输出的关联会自动可查。LLM网络异常会抛错，不能把解析错误被吞概括成所有异常都被吞。

## 效率证据及限制

第一轮 `run-04` 三组并发，是功能冒烟，不能当作稳定性能排名。100条轻量合成消息均为一次模型调用：Mem0默认12.8秒、加指南9.5秒、V2 37.9秒；前5批提供方报告的totalTokens合计分别56,644、56,573、19,273。Mem0输入提示更大，V2该次输出token更多（包含提供方统计的推理开销），所以延迟较低不等于token更少。

第二轮 `run-05-sequential` 顺序运行以减少本试验自身并发干扰：

| 配置 | 100条批次耗时 | 前5批totalTokens合计 |
| --- | ---: | ---: |
| Mem0默认 | 6.5秒 | 54,897 |
| Mem0加指南 | 9.5秒 | 58,521 |
| V2当前整理核心链路 | 11.1秒 | 15,636 |

三组各5次模型请求；Mem0各另做1次真实模型重放，重放未计入上表token合计。缓存命中的token由提供方单独列出，使用它报告的totalTokens，不用inputTokens与outputTokens简单相加冒充完整量，也未据此推算金额。两轮均正常结束独立原生进程。顺序轮Mem0重放前后条目数分别7→7和12→12；两个故障探针均复现。V2顺序轮将取消约定归档，并把长期维护经历保留为显著性5；首轮取消约定仍active但正文已标取消，显示模型维护决策存在波动。

现有生产业务仍可能共享提供方，单次、短且低信息密度的100条消息也不代表400条长消息或更大积压。没有对不同模型、人格或多次随机种子做统计性能基准，不据此承诺解决生产超时。第二轮V2的100条耗时明显低于第一轮，也说明不应把第一轮37.9秒当作固有性能。

本版add没有替我们按原生模型容量自动切分整批群消息；近期增量的触发、批次规划、超大单条、取消/恢复及失败游标仍需要V2处理。不能用更换库替代容量与运行合同设计。

## 接入判断

可以复用Mem0，但薄包装直接替换不满足当前范围：

1. 保留Journal、每群工作区授权、来源验证、CAS与成功游标、`/new`失败保留上下文、自动任务和控制台。
2. 若用Mem0自动add作为新增提炼，需要在提交前验证模型结构、明确整批成功与每条来源；当前空成功和部分成功的合同必须适配。单靠提示词不能修复这些运行语义。
3. 自主修订、合并、显著性和归档/遗忘仍要明确维护流程。可以选择“新增与维护分离”，但这属于下一步产品/实现决策，本试验没有把它部署。

据此暂不整包替换现有引擎。可借鉴/选择性复用的是“检索相关旧记忆 + 较轻的增量新增”和向量检索；Mem0确实提供了这些通用能力，但目前没有证明它能以更小的总集成复杂度满足全部既定需求。
