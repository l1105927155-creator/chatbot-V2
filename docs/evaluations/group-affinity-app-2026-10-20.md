# 群好感度应用：真实模型情景评估（2026-10-20）

结论：现有 Bot 能写出可运行原型、局部 Skill 和持久数据操作，但本次三个样本均不足以直接交付为可靠的长期群应用。薄弱处既包括生成代码的边界逻辑，也包括新会话中遵守自身调用流程；不能仅凭“脚本自测通过”宣称应用完成。

## 方法与边界

使用生产群当前相同的 `wb/deepseek-v4.1-flash`，固定版本DSH、正式插件版本的DshClient和真实群隔离Bash。三个独立全新群卷，各自使用默认群AGENTS/persona模板，不复制生产聊天与私人文件，不连接QQ。与生产群自定义人格和完整AstrBot消息链并不等价。

每组四轮：先给需求、检查只拟方案且不改文件；然后由评测器在隔离群里模拟确认方案并选择推荐默认值；新建独立Session，输入成员感谢并自然接话；再查询该成员实际保存的状态。该模拟确认不代表用户批准在真实群实施好感度系统。

原文、较长改写、收敛改写各一次，不是统计可靠性实验。三组正式全局指南均未修改。评估不对产物补丁修复后再打分。

- original：186.0秒，4轮，方案阶段改动文件0个。
- refined：204.25秒，4轮，方案阶段改动文件0个。
- concise：143.98秒，4轮，方案阶段改动文件0个。

## 独立反例复核

复挂评估群卷，在真实受限Bash中对独立数据副本执行，未更改原产物快照或原聊天数据：

1. refined的record拒绝delta=0，退出2，没有独立touch/init入口。无法完成普通首次直接交流零分建档。
2. refined对同一条+2历史连续冲销两次均成功：2→0→-2。重复冲销不是幂等，27项测试未覆盖此反例。
3. concise先以互动e1建立0分记录成功；随后以相同e1提交+2被去重拒绝，退出2。首次交流既要建档又要记分时，接口不支持按同一互动完成。
4. concise已建档成员只改昵称、delta=0时被拒绝。昵称更新不应依赖一定发生情感变化。

独立静态审查还发现concise仅追加时持锁，读取、查重和计算未在同一锁内；未在本次复核里进行并发压力试验，因此只记录为未消除的代码风险。

原文组把相同业务规则重复写进根AGENTS、应用AGENTS和Skill，后续修改易漂移。改写组遗漏应用AGENTS，说明不能假定它会自动遵循尚未写入全局教程的工程约定。

## 建议的指南分工

| 位置 | 应承担的职责 |
| --- | --- |
| 全局development | 识别群应用开发需求，路由到群应用教程；保留通用开发与验证原则 |
| 全局group-app-development（建议新增） | 从需求→待确认方案→实现→真实会话验收→交接的完整做法，以及轻量应用结构模板 |
| 全局skill-authoring（已有） | 本群Skill的创建/更新、元数据、目录发现、下一请求读取验证；无需另造一套skill-create运行平台 |
| 本群AGENTS | 简短的已启用能力索引和触发时机 |
| 本群persona | 表达风格及性格，不嵌入存储、脚本、迁移说明 |
| 应用目录AGENTS | 应用维护契约：用途、结构、数据不变量、验证方法、恢复入口 |
| 本群应用Skill | 日常何时使用、读什么、怎样调用、如何确认成功；按需指向应用资料 |

当前只自动注入工作区根AGENTS与persona；子目录AGENTS不会因同名就自动加载。开发教程应明确让Skill/开发流程读取应用AGENTS。运行规则保留一个权威来源，其它文件用索引引用，避免重复粘贴。

建议默认结构（小应用按需简化，不要求安装框架）：

```text
/workspace/AGENTS.md                   # 一小段应用入口
/workspace/persona.md                  # 维持群人格
/workspace/apps/affinity/AGENTS.md      # 开发/维护约定
/workspace/apps/affinity/app.py         # 小型实现
/workspace/apps/affinity/data/          # 真实持久数据
/workspace/apps/affinity/tests/         # 隔离样例和验证
/workspace/skills/affinity/SKILL.md      # 可发现的日常使用入口
```

教程需要明确“确认标准”：保留成员已确认机制；新增玩法单列建议；选择本群现有工具和标准库能完成的最小实现；测试样例与真实成员分离；状态修改有恢复手段；用跨Session的实际对话检验入口、身份、持久化、重复互动和查询，而非仅跑自己写的单元测试。发现未通过项应报告并继续修复，不能宣布完成。

好感度这种依赖日常判断的功能，还有一层持续可靠性：Bot只在实际被唤醒、处理互动时运行，Skill描述不等于确定性的事件监听器；数值边界与幂等可以由代码确保，是否主动调用和情绪判断仍需模型情景评测。这次不据一个成功样本宣称长期可靠。

## 已实际测试的收敛提示词

下面是concise组原样输入。相比原文，它把实现细节交给指南，并补上身份、持久化、重复记录及范围说明；没有把所有教程再塞回成员提示词。它的方案与产物仍有上述缺陷，不能称为已验证可靠的最终解。

```text
给本群设计一个能长期使用的好感度应用。先给简短方案、两个聊天例子，以及最多3个必须由我决定的问题；我确认后再创建或修改文件。

核心规则：
- 你对成员的亲疏冷暖完全由好感值决定。初始0，范围-50（深恶痛绝）至50（心驰神往）。
- 只有与你直接交流过的成员才建档，以成员身份区分，改昵称仍是同一个人。
- 根据对方如何对待你，结合现有persona的性格，判断是否加减。冒犯会降低好感，过度迎合与奉承也可能惹你反感；普通交流可以不变。单次通常不超过5，同一次互动只记录一次。
- 分值与必要的简短变动依据持久保留，开启新会话或重启后继续使用。成员能自然询问自己的好感状态。

第一版只做好这些核心能力；扩展机制作为可选建议单列。实现形式和维护方法由你按现有开发指南安排，让后续会话能发现并使用这项群能力，群成员只需描述需求。先说明方案，不要现在开发。
```

## 用户后续确认的应用约定

以下约定更新好感度应用需求；前文是历史评估样本，不代表这些产物已满足新要求。

- 范围固定为-50至50，不增加调整上下限或档位参数的配置功能。
- 应用 Skill 包含查询持久分值与变动记录的操作流程。成员查询时，以成员身份调用查询接口，按实际记录回答；回复同样受其当前好感度影响。`get_affinity(member_id)`仅为接口示意，实际名称由实现确定。
- 好感变化成功保存后，在当前回复末尾追加实际变动：正向如`好感度UP (+1) ↑↑↑`，负向如`好感度DOWN (-1) ↓↓↓`。显示实际生效的差值；没有变化时无需添加。保存失败时如实处理，不把拟议变动显示为已生效。
- 成员分值和变动记录仍是应用持久数据；Skill负责怎样查询、更新和表达结果，通过引用使用数据，不把随时变化的成员记录抄入Skill正文。
- 以上是本群好感度应用的规则，放入其应用AGENTS与Skill分工中，不作为所有群应用的全局行为要求。尚未据此开发或部署生产应用。
