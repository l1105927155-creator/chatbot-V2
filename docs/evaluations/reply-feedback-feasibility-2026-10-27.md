# QQ 回复反馈机制调研（2026-10-27）

## 结论与边界

适合引入轻量、可定位的用户反馈收集；是否值得增加自动影响回复的功能，需要先验证它相较当前直接口头纠正带来的增益。当前项目没有实现此闭环，本轮仅只读调研并记录，不修改线上指南、人格、模型、消息处理或记忆规则。

针对用词，明确的局部反馈有机会从下一次模型调用起影响表达；单独保存一个负分没有这个效果。下一轮生效与稳定遵循是不同的验收目标。本轮没有运行新的模型对照，不能声称已证明即时或持久改善。

## 外部功能的实际作用

- [Streamlit st.feedback](https://docs.streamlit.io/develop/api-reference/widgets/st.feedback)提供点赞/点踩等评分组件与回调。组件文档没有承诺自动调整模型。
- [Chainlit on_feedback 源码](https://github.com/Chainlit/chainlit/blob/main/backend/chainlit/callbacks.py)提供收到反馈后的业务回调，开发者需要实现如何处理反馈。调研的是其公开当前源码，不是本项目依赖，不据此新增依赖。
- [Langfuse User Feedback](https://langfuse.com/docs/observability/features/user-feedback)将分数与执行轨迹关联，用于筛选问题、构建评估数据及安排改进。其记录评分流程本身不自动修改我们的模型或提示词；显式反馈还存在低参与率与负面反馈偏多的采样偏差。
- [OpenAI 官方 Codex 文章](https://developers.openai.com/blog/mastering-codex-remote-for-engineering)将 `/feedback` 描述为与当前会话关联的产品反馈。这不证明截图中的点赞/点踩会即时更新个人回复策略；截图只证明存在评价入口，具体消费链路未证实。
- [OpenAI 模型优化指南](https://developers.openai.com/api/docs/guides/model-optimization)区分评估、提示词改进和微调。[评估实践](https://developers.openai.com/api/docs/guides/evaluation-best-practices)建议从生产数据和用户反馈构建评估材料；收集之后还要明确如何使用。
- [Reflexion 原论文](https://arxiv.org/abs/2303.11366)通过语言反馈与文本记忆改变后续尝试，无需更新权重。它支持“通过上下文利用反馈”这一技术路径，但其实验并未证明中文QQ群口癖可以靠一次差评稳定消除。

## 当前工程基础

1. `astrbot-plugins/v2_journal/journal.py` 的 Journal 按平台消息记录，已有 platform、bot、conversation、message_id、reply_to 与正文，可以定位具体短句；不需要另存第二套聊天历史。
2. Journal 无模型 turn ID。一轮回复可能由多条独立 QQ 消息组成，不能靠邻近时间直接认定它们属于同轮。评价单条气泡可以先做；若界面宣称评价整轮，需要补可靠关联，不能从引用目标推断。
3. `astrbot-plugins/v2_journal/main.py` 当前绑定 message、message_sent、notice.group_upload；未找到评分反应接收链路。`upstream.lock.json` 未锁定 NapCat，本地未证实其当前安装版本及表情回应事件支持，不能承诺直接点 QQ 表情即可接入。可先用引用消息加明确反馈文本的方式验证效果，原生表情入口单独验证。
4. 当前记忆是对经历的主观理解，每条绑定真实 Journal 来源。`dsh/plugins/agent-profile/memory-guide.md` 支持保留偏好；`docs/phases/group-memory-2026-10-26.md` 明确不常驻注入，前台按需检索。每日整理或 `/memory` 不保证下一轮读到该偏好。
5. Memory 的 weight 表示长期显著性，不能复用为满意度。Affinity 表示成员关系，也不能因用户给差评而扣好感。反馈应保留评价者、目标和理由；个人表达偏好不能自动升格为全群约定。
6. `docs/evaluations/qq-expression-habits-2026-10-27.md` 的已有真实模型实验表明，反例和禁词并未稳定解决问题，发生过“这点我认”向“这句我记着了”等表达迁移。这不是新反馈机制的实验结果，但足以约束其验收标准。

## 如何理解“立竿见影”

| 做法 | 对下一轮的作用 | 仍需验证 |
| --- | --- | --- |
| 只在后台记录 👎 | 若未提供给模型，不会经由该记录改变下一轮请求 | 收集数据是否有后续使用价值 |
| 在当前聊天中引用并纠正用词 | 模型能在上下文里看到，可立即尝试遵循 | 近义迁移、持续性、上下文压缩后的保持 |
| 明确评价“此处用词生硬”，下一轮提供目标与偏好 | 具备立即生效的工程条件，不必每次写长评 | 模型是否理解原因、是否过度回避正常用语 |
| 将已确认稳定偏好持久保存并在适用请求中提供 | 可跨会话提供同一偏好 | 归属、冲突、撤销、相关性及提示词负担 |

按钮可以简便，但其含义要明确：整条回复的差评可能针对事实、语气、长短、分段、工具行为或人格。即便选中了一个短语，也仍可能不知道用户希望更亲近、更直接还是更口语。因此可将入口限定为“用词生硬”，允许补一句理想说法；没有理由时保留不确定性，不擅自生成永久禁令。

以“这个我认”为例，可测试的偏好表述是：“纠错时直接给出正确内容并简短承认错误；回应善意时直接表达当下感受。”保留原始差评作为来源；不能只在后台把它换成另一个接收/认可动词。

即时反馈只可能影响之后开始的模型请求，无法改变已生成或已经发送的消息。初步方案不自动重发或改写已发内容。

## 最小验证建议

先复用沙箱与现有真实回复样本，不急于开发评分面板。冻结模型、Persona、发送指南与历史，对比：无反馈、仅 👎、局部表达差评、差评附具体偏好。每组从相同上下文独立开始，包含一次同类回应和后续不同场景；另测新会话按需提供已确认偏好，避免把短期上下文效果当长期学习。

人工查看：原问题是否减少、是否换成近义套话、情绪张力是否保留、必要区别是否被误删、是否引入反复道歉或附和。正面反馈也记录具体喜欢的部分，避免误以为整条回复的所有特点都应模仿。用未参与修改的新场景复核，完整保存失败，不以禁词命中数或一个好样本判定成功。

只有带反馈的方案相较直接口头纠正体现出可重复的收益，才值得做持久化和入口：最低数据为本群身份、目标 Journal ID、评价者、评分、可选短句/理由、时间及修改/撤销状态。正文仍引用 canonical Journal。具体存储和权限实现留待实施阶段决定，本轮不建立新反馈平台或训练管线。

若后续试点，由测试群开始，明确“已记录”和“后续请求已使用”两个状态，不能把收到差评就显示成“已学会”。个人反馈先用于与该成员的相关交流；群级默认表达的改变由现有维护权限控制。模型不会因为按钮本身更新权重。

## 未验证项

当前 NapCat 反应事件能否完整提供目标、操作者及撤销；整轮发送关联的可用运行时字段；当前 Flash 对即时局部反馈与跨会话偏好的真实效果；长期成本及反馈冲突处理。以上均不能用现有界面截图或已有指南实验替代。
