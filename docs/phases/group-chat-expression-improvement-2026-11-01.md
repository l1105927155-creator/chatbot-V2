# 群聊 Agent 表达质量整改：第三阶段（候选改善与可验收交付）

日期：2026-11-01。状态：**待开发助理可行性评估、实验与实施；不得因完成实验而宣布整改成功**。
前置：[总目标与双阶段验收](group-chat-reply-relevance-2026-11-01.md) · [第二阶段任务](group-chat-reply-relevance-next-round-2026-11-01.md) · [第二阶段结果](../evaluations/group-chat-reply-relevance-next-round-2026-11-01.md) · 基线提交 [4cc63c2](https://github.com/l1105927155-creator/chatbot-V2/commit/4cc63c2bfbfad5a2eb3052890a02cf7d270533d6)。

## 1. 唯一成功目标

> **Bot 的聊天表达质量取得稳定、可验证的改善。**

这里的「表达质量」不是字数、气泡数或安静程度，而是：对当前交流有用、准确、自然、有个性；简单任务不默认公开文件路径、操作流水和不相关旧话题，复杂追问能提供充分证据，失败／不确定情况能如实说明；必要时能够主动提出建议、反驳、开玩笑或深入讨论。

**不要再将排查、脚本数量、27 格全部跑完、工具合同通过或某个正例视为整改完成。** 这些仅是获得可信改善的前置条件。没有正向、可复核且不牺牲正常交流的结果，应报告「未改善」而不是累计研究进度。

保留用户此前的设计原则：不增加统一字数／每轮消息数上限，不靠关键词截断、硬拆句、对所有消息做语义审核／二次 LLM 改写，不牺牲群聊主动性、Persona、工具能力及重要异常信息；程序安全与平台限流另论。

## 2. 第二阶段的已知边界与第三阶段聚焦

第二阶段对 18 格完整任务、9 格旧话题作隔离实测：新交流原则 B 在简单记录三次中仅一次避免主动汇报路径和字段，没有可重复的整体优势；明确追问时仍能充分解释，真实权限拒写能如实告知。P1 合成新会话没有复现无关巡查话题的主动延伸，不能将原案历史因素排除。

另有一条具体反例：`P0-permission-B-r2` 已通过 `qq_send_origin` 公开解释只读无法留档，随后 final 又重复同一失败与后续请求；两次发送有不同 attempt/回执/Journal，**是模型的交流意图重复，未证实程序重投**。原案先完成记录再经三个工具消息加一个 final 主动公开细节，亦属于模型决定向群里说什么的问题。

第二阶段还证明，长 final 的宿主无损分组可能形成多个气泡；此现象与模型主动调用 `qq_send_origin` 必须分别统计，不得把任何多气泡都判错。已有早期 G/D 描述对齐实验未取得稳定优势：**不准把简单重写工具描述预设为有效，更不准直接动发送协议。**

第三阶段聚焦两个可分辨的机制假设：

- **H1：结果选择失当。** 模型取得真实操作结果后，自动把所知的操作细节当作对群成员有价值的回复。即使只生成一条 final 也会过度汇报。
- **H2：发送承接失当。** 模型对「工具已提交公开消息」「final 应承担剩余回应」的语义边界理解不稳，可能把同一交流目的再说一遍，或把每个过程事实分开公开。

这只是待验证假设，不等于机制已被证明。

## 3. 实施顺序：先识别有效干预，再考虑正式改动

### T0：复核证据与形成极小候选（必须先做）

先检查当前 `main`、实际部署版本、群有效 AGENTS／Persona、`dsh/profile/agent-group-sandbox.md`、`dsh/plugins/agent-profile/decision-guide.mjs`、`astrbot-plugins/v2_dsh_router/mcp_server.py` 与 `service.py` 中的真实发送合同。核对旧 G/D 试验的具体条件与局限，**不能用同一措辞重跑同一实验再声称新候选**。

产出不超过两个互不混杂的*最小候选*，分别对应 H1 和 H2：

- **候选 R（结果表达）：** 明确区分「任务执行事实」与「当前群聊需要告知的结果、限制和必要后续」。必须允许被追问时提供详细操作信息、有意义的主动建议和长讨论。优先在**已证可生效**的提示载体上做最小修改，不覆盖群自定义内容。
- **候选 S（已发送与终末承接）：** 使模型认识到 `qq_send_origin` 提交的是可能被群成员看到的消息，而非不可见中间草稿；final 只补尚未表达且相关的内容。必须保留 `submitted` 不等于 QQ 实际确认、非空 final、失败兜底、防重放及多成员发送合同。若候选只能通过破坏这些合同实现，标记不可行并停在评估。

候选选择以证据为依据；如同一提示层无法隔离 H1/H2，先做请求投影上的单变量探针，不能假装得到了独立因果结论。任何运行时新增语义钩子，必须先验证注入位置、模型实际可见性、原生对象不可变性与权限边界；**既有实验用 provider seam 不得未经生产合同验证直接上线**。

### T1：分别验证 H1（不要以「短」取胜）

先固定工具与已完成任务的事实，隔离*回复决策*，至少包含：

1. **简单成功**：已按要求完成记录；期望自然确认，不主动报路径、备份、字段流水。
2. **明确追问**：同一事实，但成员要求提供路径、修改方法和核实依据；期望完整且真实。
3. **失败／未知**：完成状态不同，真实或等价语义的故障夹具；不能因为减少消息而隐瞒失败、虚构成功。
4. **正常展开**：争论观点、讲段子或展开建议；不能把每轮都压成「收到」。

基线与 R 保持相同业务事实、模型 route、有效指南其余内容、工具 schema 和 Persona；明确注明任何历史工具结果／旧指令差异。还应在至少一组**从请求开始的完整任务**中验证，因为只测终末续接不能证明生产可行。每格保留真实请求投影、工具结果、模拟 QQ 交付、文件事实、终态和独立重复。不得改变模型参数来换取候选胜利。

### T2：分别验证 H2（只判语义重复，不判多条即错）

固定已公开发送的第一条内容与任务状态，针对以下情形进行受控续接；比较基线与 S：

1. 工具先发完整确认，后续并无新事实：不得在 final 里重述同一个回应目的。
2. 工具先发**部分**信息，随后出现影响对方行动的重要新事实：final 必须补充，不能为去重而漏答。
3. 已发失败说明，未知是否 QQ 实际送达：不得把提交回执当送达确认，也不得盲目重复发送造成两条。
4. 明确对不同成员分别发言、确有不同独立话题，或长篇正文需要自然分组：允许多气泡，不用统一发送条数衡量质量。

单独核对「模型主动 send」和「宿主分组」来源。仅在 S 明显改善已发／final 衔接且不损坏合同后，才考虑有限的跨层工具说明调整。若必须支持「只有工具发送、final 为空」，另案验证原生终态及交付协议，**不作为本阶段绕过问题的捷径**。

### T3：留出、筛选与最小可交付候选

- 实验前冻结样本、条件、重复次数、交错／平衡顺序、判定轴、严重失败定义与停止规则；对照须具有相同初始状态与可对齐模型输入。每组至少重复三次；小样本只做方向性筛选，不做统计显著性或广泛改善宣称。
- 先分别比较 R、S 对各自目标的改善；**只有单项有效**，才考虑组合 R+S，并使用新留出案例检查交互，不能先混合后倒推是哪句提示起作用。
- 留出覆盖真实不同用户意图：简单确认、详细追问、任务拒绝、已发信息后续接、讨论／幽默／主动反驳、多成员互动及至少一类长篇交付。包含未用于调整候选的原案近似重放及较长会话／压缩后的检查；如成本或条件阻塞，必须明确未覆盖而不是降格宣布全面完成。
- 逐例评阅**整轮实际气泡**：交流意图满足、必要信息是否遗漏、无关操作说明、语义重复、未经证实的事实、人格自然度。失实成功、错引证据／错误哈希、丢失重要异常应单列严重失败。指标不能以平均字数、气泡数、段落数或单一匿名模型分数取代用户判断。
- 候选**晋级条件**：与固定基线比较，在目标坏例中多次重复出现实质改善；在正向控制与留出场景未引入严重事实/任务状态退化；差异可归因、能在真实生产兼容的路径实现、有可审阅最小 diff 和回退方案。只有一条漂亮回复、只减少气泡、或仍有明显事实误报，均不得晋级。
- 若 R 和 S 都没有可信改善：交付清晰的阴性结果、影响因素与最多一项下一步建议；**停止继续堆新规则或扩大研究框架**，回到候选假设或模型适配能力可行性判断，不宣称修复。

## 4. 从实验走向真实改善的门槛

本轮应争取交付**一个有正向证据的最小候选**，而不是再开发一套无终点的实验系统：

1. **研发验证**：完成基线和候选的受控对照，解释真实提高在哪里、仍失败在哪里，并验证代码/配置/权限/发送合同不退化。
2. **代码审查**：由本会话审查助理复核真实 diff、模型输入与模拟消息证据、确定性回归和回退流程。未取得私有原始证据时要区分研发报告与独立复跑。
3. **受控群试用提案**：候选通过前两关后，提交明确的目标群、作用范围、原 SHA、备份、回退和观测场景，**征得用户批准后才在测试群部署**；不能因为有脚本就自动覆盖群现有 AGENTS、重启生产或主动向真实群发送消息。
4. **实际效果验收（最终决定权归用户）**：用自然群聊场景判定 Bot 是否更懂该说什么，同时保留表达与人格；不满足时回退或继续定位。只有这一步通过，才可说「实际聊天效果已获验收」。

禁止直接动无证据的基础收发、群规、Persona、记忆、affinity、权限与历史读取机制。候选若涉及任一模块，必须提供独立依据及回归。不预先要求它们与 R/S 同轮变更。

## 5. 交付物与验收口径

开发助理至少提交：

- `docs/evaluations/` 下本阶段报告：基线/候选方案、为何区别于先前阴性实验、冻结条件、每格证据与失效案例、事实核实、结论及适用边界；
- 最小候选 patch 与使用范围，或若全部阴性则明确不更改生产配置；拟修改文件、原因与回退步骤；
- 模拟 QQ 所有出站的来源关联（MCP vs final vs 宿主分组）、已发与 final 的语义承接、真正文件状态及错误/未知结果；
- 可复核测试命令和结果、留出测试、未覆盖场景、原生实际输入证明、清理与数据隔离证据；
- 面向用户的**结果表**：哪些自然交流行为比基线改善、哪些退化、哪些未证明；不能只报运行成功率。

**代码验收标准**：实施忠于证据和最小范围、测试可复核、不破坏既有合同、未夹带硬性聊天配额、未擅自部署。**效果验收标准**：用户认为真实群聊表现更自然、相关且可靠；长短因语境而异，非必要的内部工作信息减少，合理主动性保留。

**本阶段若全部完成但没有表达质量改善，结论仍是「未达核心目标」；不得将阶段任务完成写成整体整改成功。**
