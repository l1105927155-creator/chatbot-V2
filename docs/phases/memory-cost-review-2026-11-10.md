# 群记忆成本：原因假设与优化方向（待数据求证）

> 2026-11-10。此文仅整理已有实现线索及候选方向，供开发助理调查、评估；不是整改结论、实施授权或预期节省比例。实际瓶颈、方案收益与质量影响均需从生产记录或隔离回放求证。

## 背景

用户提供的近期中位用量：普通回复143轮，非缓存输入1,255、输出180 Token；记忆整理198次，非缓存输入33,215、输出15,979 Token。两类请求的处理范围不同，不能据单次中位数倍数推算总浪费或费用。输出计量是否包含推理 Token、缓存输入如何计价，也要按实际提供方 usage 核实。

疑问：记忆整理会再次读取部分在正常聊天中已经投影给模型的消息，是否可以复用前台的理解并降低总成本？同时，整理链路自身可能存在更直接的重复请求，需要先区分来源。

## 代码与已有记录支持的线索

- 目前群记忆以 canonical Journal 为完整来源；后台增量和 `/new` 消化未整理范围，独立于前台会话。前台请求不一定包含所有群消息，尤其是未唤醒 Bot 时的群聊，因此「同一份内容重复输入」并不总是完整等价的两份输入。
- 当前整理不止一次生成：生成记忆变更后还会对**每条变更**单独发起模型事实核对；核对请求可包含本批原文及相关历史证据。重复上下文可能增加输入及输出开销，但这是为了修复已复现的主体、时间、行为状态等事实错误，不能直接删除校验。
- 既有[批量效率记录](batch-efficiency-2026-11-06.md)已经取得聚合用量，并发现核对阶段串行调用；尚未掌握完整的分阶段用量及成本占比。50/100/200消息投影的 UTF-8 字节差异也不等于模型 Token 或最终费用差异。
- 曾做过[Mem0 对照](../mem0-evaluation-2026-10-29.md)：不能据该样本认定整包替换可以省 Token；现有系统的来源核对、原子提交、修订和遗忘语义仍需保留。外部系统的增量提取、后台深度整理、前台主动记忆仅作为设计启发，不是本项目收益证据。

## 候选方向（按取证结果决定是否试验）

1. **先拆清成本来源。** 从可用的真实记录定位生成、逐条核对、上下文构造、重试/失败等阶段的调用次数、Token、延迟及费用；缺少字段时在隔离环境针对性补测。重点判断大额输出来自哪一阶段，不预设输入重复是主要瓶颈。
2. **降低事实核对的重复上下文。** 评估依据记忆所引用消息、相邻对话和相关历史证据构建核对输入，而非每条都无条件带整批原文。必须覆盖未被引用但会推翻草稿的反例；现有防张冠李戴、事实升级、跨日时间错误的样本应作为退化门槛。缩小范围是否能维持质量，未知。
3. **将轻量增量形成与较重的跨期维护区分。** 日常可以先提取新经历，必要时仍处理明确更正；合并、强化、遗忘等复杂维护可以评估更低频的独立处理。不得直接照搬 ADD-only 而丢弃已确认的修订、来源和记忆演变规则；维护延后是否累积额外成本也需计入。
4. **检查既有记忆选择及消息投影。** 评估是否反复带入与本批无关但权重高的旧记忆，以及结构字段能否无损精简。改变检索/批大小前，先确认同一范围完整处理的 Token 和事实质量，而非仅比较 prompt 字节或单次响应。
5. **把回复阶段顺手记忆作为独立实验。** 正常回复可能已经理解部分消息，可研究有限的主动记忆写入；但会增加前台工具、输出和延迟，也无法覆盖未唤醒 Bot 时的群聊。后台仍需负责未覆盖范围，前后台共享来源的去重、竞争修改和游标语义要验证。暂不默认改为前台主导。

## 评估建议与边界

- 开发助理自行寻找可用的生产真实数据；无法从旧计量还原的部分明确写「缺测」，不推算成确定结论。优先复用当前只读记录、原生模型路由和现有隔离回放，不引入新评测平台。
- 在同一批 Journal 原始消息、已有记忆、模型、Persona、有效指南、核对要求下做可比实验。至少记录非缓存/缓存输入、输出（可区分时包含推理）、请求次数、耗时、失败及回退成本；比较**同一消息范围最终处理完成后的总成本**，而不是仅比较单个调用的中位数。
- 质量验证要覆盖成员归属、反驳与自述变化、时间顺序、动作是否完成、Bot 主观理解及跨批关联。来源 ID / JSON 合规不能代表语义正确；必要时观察后续召回效果。
- 保留 Journal 的完整事实来源、群隔离、来源校验、原子提交与游标、失败范围和 `/new` 约定。未证实收益前不调整生产阈值、不取消事实核对、不迁移记忆框架、不直接上线候选。
