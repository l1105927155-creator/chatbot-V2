# 群聊 Agent 回复相关性：排查、整改建议与双阶段验收（2026-11-01）

状态：**待开发助理可行性评估与实现；尚未声称修复。** 本文是研发交接与验收约定，不直接改动生产群配置或消息行为。

## 1. 目标与非目标

**目标：让 Bot 只说当前交流值得说的内容，而非一律少说。** Bot 同时具有聊天伙伴和 Agent 能力；内部可以完成复杂操作，外部按交流意图选择表达。确认简单操作时可以只说「记下了」，对方追问、重要异常或实质风险需要解释时应当说明；讨论、吐槽、段子、争论和有价值的主动建议可以自然展开。

复现案例（用户提供的 2026-10-31 群聊截图）：对方询问是否记录违规行为，Bot 连发四个气泡，依次确认记录、详细描述修改的章节和条目、报告备份文件名、又主动插入一段与当前请求无关的巡查错误分析。**期望行为是简短确认任务结果；不是必须逐字输出固定模板。** 若记录失败，必须如实说明；截图中的文件写入事实尚未由运行时证实，不能把 Bot 自述当成已完成的证据。

明确不做：统一每轮总字数、消息数、每条字数/段落上限；「网络段子除外」式例外堆叠；按路径/关键词直接删正文；不区分场景的自动缩写或语义审查器；为了让指标好看而禁止主动发言、抹去 Persona，或将所有回复固定为「好的／收到」。**QQ 平台的安全限流、风控、协议字段长度属于另一类技术边界，不在本需求中取消。**

## 2. 当前证据及边界（评估前须复核最新源码）

### 已能从当前仓库代码确认

1. `dsh/plugins/agent-profile/decision-guide.mjs` 在 group-sandbox 的系统提示 assembly 中异步读取当前工作区 `AGENTS.md`；`persona.md` 亦有群级独立入口。**代码具备每次请求加载的机制**，但不能据此断言截图那轮实际注入成功、内容正确或模型遵循。群级共享决策文件是 `dsh/plugins/agent-profile/group-decisions.md`，不是普通 owner/safe-chat 的 `decision-guide.md`。
2. `astrbot-plugins/v2_dsh_router/mcp_server.py` 的 `qq_send_origin` 每调用一次即可另发独立消息；`qq_prepare_reply` 仅设置最终消息的 @/引用，不发正文。`service.py` 中工具发送走 `send_kind=mcp`，轮次最终正文走 `send_kind=final`，当前 `_handle_locked` 对最终文本仅调用一次 `send(reply)`；**不要把四个气泡未经核验就认定为“三次 mcp＋一次 final”。**
3. `runtime_audit.py` 提供 `turn_id`、`session_id`、`send/start`、`send_kind`、`send/receipt`、工具事件等关联线索；`submitted=true, platform_confirmed=false` 不是 QQ 已送达证明，需关联 canonical Journal 与平台回执。
4. `reply_safety.py` 主要阻断明确协议/内部控制文本，并不判断中文日常表达是否冗余；当前发送链没有统一「表达相关性」审查。不能据此推导必须增加过滤器。
5. 2026-11-01 修改的 `dsh/templates/group/AGENTS.md` 已加入「根据交流意图选择表达，不把操作流水默认为聊天内容」的模板约定。依据 `docs/workspace-guides-skills.md`，**模板更新只影响新初始化群；已存在工作区文件不会自动被覆盖。**
6. 还要关注跨层指令：`dsh/profile/agent-group-sandbox.md` 和 `decision-guide.mjs` 的 Shell 说明在慢操作前要求简短等候提示；`qq_send_origin` 的工具描述也提及等候、独立接话。这类提示可能合理，但应检查是否在本案诱发了多余的过程播报，而非直接删除。

## 3. 排查顺序与需要回答的问题

| 优先级 | 排查方向 | 操作和证据 | 判定问题 |
| --- | --- | --- | --- |
| P0 | 本案真实发出路径 | 用入站 message_id／时间／会话定位 audit `turn_id`、SID、原生 assistant/tool_call/result、`send_kind`、平台回执、Journal 的四条出站。只读取证，按现有脱敏规范保存。 | 是同一轮还是多轮？各气泡来自 `qq_send_origin`、final、程序兜底还是其他插件？有无重发、重复调用或来源错配？ |
| P0 | 实际提示输入 | 核对本轮和工具调用后请求中当前群 `AGENTS.md`、`persona.md`、共享 `group-decisions.md`、Profile、Skill、工具说明的**有效投影**；核对生产群指南版本与已提交模板的差异、读取异常。 | 指南是否真的缺失、过旧、有互相竞争的表达职责，还是已注入但没被模型落实？ |
| P1 | 「内容为什么被说出来」 | 对照该成员提问、该轮实际完成结果、之前 Journal 话题与模型工具返回，逐句标注：必要结论／必要异常／应按请求提供的细节／未被请求的工作报告／无关建议。 | 文件路径、备份名、六条细节和「顺便说一句」分别基于何种输入？是否与旧话题、Skill 的汇报要求或模型惯性有关？ |
| P1 | 已发消息与 final 关系 | 检查中间 send 已发内容是否仍被 final 当作未回答；不同成员 @／引用、send 回执不确定、final 为空、取消或失败时怎样结束。 | 有没有相同回应意图被复述、错误补答或遗漏重要事实？ |
| P2 | 长历史与压缩假设 | 仅在本案可取证时检查 context token、有效 system、summary/compaction、重复旧指南和旧坏回复；必要时冻结事实、模型、Persona、工具及近期请求做隔离对照。 | 历史规模/旧示例是否相关？**不能因会话很长就断言指南被压缩失效。** |
| P2 | 记忆与自述偏差 | 检查 `memory/preferences.md` 是否实际被写入，是否仅作手工索引、有没有被自动加载；区分群记忆服务与工作区文件。 | Bot 是否把「我写了记录」误当成「今后每轮都会先读」？不要为解决表达问题擅自加常驻文件读取。 |

优先查看现有 audit、canonical Journal、native Session；不能取得原始 trace 时应注明无法证实的环节，不通过截图臆造 mcp 次数。不要改写生产会话来构造证据。上述检查只定位行为，不以新增大规模日志为前提；如确需补观测点，先复用现有 trace ID 与 Journal 关联，避免重复存储敏感聊天正文。

## 4. 改动建议：先评估，按证据选择最小方案

### A. 交流原则（优先，已有新群模板）

以「是否有助于当前交流」决定表达内容；日常聊天允许深谈、玩笑、观点、反驳和自然延伸。执行任务默认说明**真实结果与必要后续**，不是逐项汇报 Shell、文件路径、备份和工具细节。只有被追问，或者风险、异常、授权、未完成状态、影响后续操作等信息实质重要时才展开。

开发助理先对比**现有群工作区**与新模板，给出可审阅的最小差异和部署迁移方式。不要在代码中强行覆盖既有 AGENTS、Persona、群规或成员资料；模板不能自动覆盖生产群，这一点必须显式说明。不要把具体截屏台词固化成通用短回复范例或一串禁词。

### B. 发送职责／工具描述（需因果验证）

如本案和隔离对照显示职责歧义，审视 `agent-group-sandbox.md`、`decision-guide.mjs`、`qq_send_origin` 描述以及最终正文之间的边界：

- `qq_send_origin` 是**已经公开发送的群消息**，不能把它当不可见的中间工作日志；后续 final 不应复述已完成的同一交流目的。
- `qq_prepare_reply` 仅设置最终正文的 @／引用，不应被误认为发送过一条。
- 简短等候提示仅在确实需要向群友交代等待时有价值；完成后按结果自然收尾，**不要固定发送「开始／过程／完成」三段式进度**。
- 需支持向不同成员分别交流、补充新事实、独立长内容、合并转发及主动聊天；不要简单禁止多次发送。
- 处理既有「空 final 触发失败兜底」合同：若提案允许工具消息完成全部答复，必须先解决空 final、发送确认、未知送达状态及重试安全；否则保留可解释的「工具先发／final 收尾」合同，不能仅以新增指令假定闭环。引用 [既有定位报告](../evaluations/reply-root-causes-2026-10-29.md)。

**先做小规模可复现 A/B，再决定是否改写跨层 Profile 与工具契约。** 已有 G/D 实验未达到稳定收益，禁止直接宣称「对齐工具描述」必然解决。

### C. 程序边界（仅修确证缺陷）

若证实程序重复提交、补答状态错误、引用错位或日志错误，针对具体状态不变量做确定性修复。可以保留既有平台长度校验、限流、失败保护，但**不得为语义表达添加 50 字／3 条等硬上限、按句拆分、语义重写、关键词屏蔽或隐形第二回复模型**。若开发助理认为这些必不可少，应单独提交权衡与证据，不纳入默认实现。

### D. 其他关联因素（按需独立处理）

若本案涉及任务失败循环，复用已验证的失败收束方向；若与 `skill-authoring`、affinity 通知、记忆操作相关，应分别核对其**真实职责**及是否要求不必要公开播报。不要以削弱现有任务、权限、记忆和好感业务换取更少的聊天消息。

## 5. 实施与对照流程

1. **先交可行性评估**：为每条排查结论给「证据路径／已证实／未证实／不适用」，列出选定方案、拟改文件、预期解决的问题、可能伤害的正常行为及回退方法。证据不足时可先提交诊断结果，不应因任务名叫「开发」而强行实现方案。
2. **冻结基线**：记录 main SHA、实际部署版本、模型 route、当前生产群指南与 Persona 摘要/哈希、关键 Skill 与工具说明；对当前案例只读取证。实验不向真实群随意发送测试消息。
3. **最小干预对照**：以相同业务事实/初始工作区/工具能力/模型和配置，分别测基线、仅新交流原则（现群按审阅方案迁移）、以及有必要时的发送职责候选。不要一次混入多个功能改动；已有 `scripts/reply-intent-trial.py`、`tests/native/reply-intent-experiment.mjs` 可评估复用，不能直接把沙箱 seam 作为生产修复。
4. **独立回归与留出场景**：每组重复，包含原案回放和未参与修改的场景。保存实际模型输入投影、工具调用、真实模拟 QQ 气泡、回执、Journal、终态。协议/环境失败与表达失败分开，保留失败样本。
5. **提交代码与证据**：代码、自动化回归、实验结果、运行方式、回退说明分别提交；所有外部副作用必须有原有授权，生产文件不因模板变化被自动覆盖。最终由本会话助理复查代码与测试，再由用户在真实群聊中验收效果。

## 6. 验收标准（两级，不以单一长度指标冒充体验）

### A. 代码／机制验收（开发助理自检，随后由审查助理验收）

- [ ] 本案四气泡已明确归因，或逐项列明缺失的 runtime 证据；`qq_send_origin`、`qq_prepare_reply`、final、回执、Journal 关联正确，没有错误地把工具提交等于平台送达。
- [ ] 能展示修改前后**实际模型请求**注入的相关指南、Persona、Profile 和工具说明，不只验证源文件存在；区分新群模板与已建立群的生效边界。
- [ ] 现有发送与空 final／已发工具消息后收尾／发送失败／未知回执／重复引用／多对象的合同回归不退化；程序侧明确导致重复或漏发的缺陷有确定性测试。
- [ ] 修改不增加固定字数、每轮消息数或语义删改规则；不破坏自主聊天、长篇讨论、合并转发、文件交付、记忆、affinity、权限及原有安全保护。
- [ ] 有可重复的基线/候选对照、真实模型 route 与关键配置、原生投影和模拟 QQ 交付证据；区分稳定可重复的工程测试与随机模型输出的观察。
- [ ] 运行既有相关 native/contract/Python 测试并给出命令与结果；新测试能在无需付费模型的情况下验证确定性契约。失败测试、跳过项和不可复现项目明确列出。
- [ ] 仅更改与已证问题相关的最小代码／指南；提供 diff、风险和回退路径，不把既有研究实验当成生产可用模块。

### B. 群聊效果验收（用户判定；代码合格不代表通过）

至少覆盖以下场景，不规定回复必须几个字或几条；以实际收到的**整轮所有气泡**判断：

| 场景 | 期望 | 不合格现象 |
| --- | --- | --- |
| ① 简单记录／改文件成功 | 自然确认结果即可 | 主动报文件路径、章节编号、备份名、每一步操作；结束后无关「顺便说一句」 |
| ② 对方明确追问实现细节 | 充分解释真实实现与可核实证据 | 机械只回「好了」，隐瞒被要求的关键信息 |
| ③ 执行失败、权限不足或送达未知 | 准确区分已完成／未完成／未知，必要时提醒影响 | 为了简短谎称成功、虚构已记录或把未知说成确定 |
| ④ 正常闲聊、玩笑、段子 | 可以有个性、有趣并适度展开 | 所有场景都只会「好的／收到」、无意义的固定短句 |
| ⑤ 深入讨论或有争议观点 | 能主动分析、反驳、提出有价值的建议 | 因「不主动建议」而唯唯诺诺，或答非所问 |
| ⑥ 无关的旧话题／非必要补充 | 能收束当前话题，不习惯性切换到旧故障或多余建议 | 问记录却主动讲另一个巡查错误 |
| ⑦ 同轮先发一条、工具处理、再结束 | 不复述已经说出的同一交流目的，必要新事实可补充 | 工具先发「记了」，final 又从头解释同样结论 |
| ⑧ 多成员交流、长篇独立内容、合并转发 | 正确选人、正确使用引用/发送方式，真正需要长内容时不被删节 | 因单气泡偏好而漏答、错误 @ 或拆碎刷屏 |
| ⑨ 重置、较长会话或指南变更后 | 重要交流原则仍能在有效请求中被找到、表现没有明显退化 | 只测全新短会话就宣称长期解决 |

验收时逐例标注：**交流意图是否满足、必要信息有无缺失、无关实施细节是否冒出、有无语义复述／话题漂移、人格是否自然、气泡边界是否合理**。不要以均值字数、平均条数、短句比例、段落数或匿名模型评阅的单一分数替代用户判断。允许必要的长回复，也允许自然的短回复。出现安全与状态事实误报时单独列为严重失败，即使表达简洁也不通过。

## 7. 交付要求与分工

**开发助理**：先评估可行性、现有证据和未证假设；确定最小整改范围，开发并提交代码/测试/报告；不得自行把实验成功宣布为用户体验验收。

**代码验收（本会话助理）**：在开发完成后检查实现是否忠于需求、核对真实 diff、测试覆盖、原生输入与发送链证据、意外行为和与现有实验结论的关系；给出通过／不通过／待补证据。

**实际效果验收（用户）**：在真实群聊中审阅行为；有权认为「变短了但没人格」「不刷屏却漏了重要内容」仍不合格。用户反馈再反向决定是否迭代指南与实现。

**提交研发评估时至少提供**：定位证据表、拟改文件清单与变更原因、未解决风险、测试命令与原始结果、可复现实验/匿名化证据路径、上线影响范围和回退方案、需要用户判断的事项。**没有证据就明确写未知，不推断业务规则。**
