# QQ 发送节奏与平台限制冷却

用户已确认 QQ 账号刚解除限制，授权增加发送保护并重启生产。此前两个模型 `TRANSPORT / fetch failed` 是独立观察，不能据此排除 QQ 账号限制。

## 本轮边界

复用 Router 的 OneBot `call_action` 钩子，不改上游、不新增发送服务。平台加载、Router 初始化和 AstrBot 加载完成时绑定现有 aiocqhttp 客户端；既有事件绑定保留。每个客户端共享发送锁，群聊、私聊、转发和文件发送均在真正调用 API 前等待随机 1.5～3.5 秒。其他查询 API 不限速。

只根据失败结果或异常的结构化 `result` 中明确的风控、账号冻结、发送频率限制文字开启 300 秒冷却。冷却中直接拒发，不等待到期后补发，不自动重试原消息；到期后的新发送可以继续。网络超时、未知数字错误码、群禁言不触发账号冷却。成功结果中的聊天文字不参与识别。仅记录固定类别日志，不记录平台原始错误或消息正文。

保留原生异常及发送回执。冷却拒发与调用 API 前的取消标明确定未送达，避免 Journal 误判文件回执缺失；调用 API 后的取消保留不确定性。卸载时让嵌套在其他插件内的旧钩子失活，避免重载叠加延迟。

## 可观测性与限制

日志固定提示 `V2 QQ platform send restriction detected`，包含冷却秒数。既有发送失败处理继续工作，冷却中的错误通知也会被拒发，不产生重复发送循环。冷却状态是进程内状态，重启清除。

平台若返回成功但对方不可见，无法仅靠 OneBot 回执可靠识别。本轮不声称能提前判断或避免所有 QQ 风控。独立 OneBot 客户端实例不共享锁；不经该客户端的外部程序发送不受保护。
