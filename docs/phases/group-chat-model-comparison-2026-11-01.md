# 群聊表达质量：DeepSeek Flash 与 GPT Terra 隔离对照

日期：2026-11-01。状态：**待开发助理评估并执行；尚无质量胜出者，不授权新的生产切换**。

关联：[表达质量唯一目标](group-chat-expression-improvement-2026-11-01.md) · [第三阶段 R/S 阴性结果](../evaluations/group-chat-expression-improvement-2026-11-01.md) · [Terra Medium 接入](../terra-medium-validation-2026-11-01.md) · [Terra 代理与生产接入](../terra-proxy-validation-2026-11-01.md)。

## 1. 核心目标和当前事实

**唯一成功标准：Bot 的聊天表达质量取得稳定、可验证的改善。** 不以模型能够连接、工具通过、回复更短、气泡更少或完成更多实验代替效果改善。既要减少无意义的操作细节、重复说明和无关旧话题，也要保留真实信息、个人风格、幽默、反驳、长讨论和必要的主动性。

此次获用户同意，**将 `openai-codex/gpt-6.1-terra` 纳入与 `wb/deepseek-v4.1-flash` 的隔离比较**。Terra 使用接入时设置的模型级默认 Medium；记录 DeepSeek 真实生效的推理配置，不擅自把不同 provider 的强度名称判成等价。对照模型的「既定可用设置」属于产品化体验比较，非同等计算量/内部推理资源比较。

注意实际生产状态：据 `docs/terra-proxy-validation-2026-11-01.md`，开发助理已将七群、Owner 私聊及新会话默认路由设置为 Terra，九个 DSH 进程健康；**这不是聊天表达质量已验收**，也超出了此前讨论的「仅授权隔离比较，不直接切换生产」。本阶段**不再次修改线上模型、不自动回滚、不向真实 QQ 发测试消息**；先由开发助理核对线上真实状态与文档是否一致，并明确告知用户当前路由、原路由和可恢复路径。若用户决定恢复，由用户另行授权，不能假设已授权。

Terra 接入层的隔离真实调用和代理安全回归已由提交报告支持，但长期 OAuth 令牌实际轮换尚未验证；需要独立关注可用性、失效与恢复，不能把这类连接故障误计为「语言表现差」。不要将共享账号凭据、令牌或完整私人群聊数据提交 Git。

## 2. 先验明：两个模型可否公平运行同一业务任务

在隔离环境验证：两条路由均可完成真实的 DSH 原生 turn、Shell、当前群工作区读写、MCP `qq_send_origin`/`qq_prepare_reply`、final、模拟 QQ 回执／Journal 关联，并可读取同一份有效 AGENTS、Persona、群级 Profile、Skill 与工具说明。逐模型记录实际 provider/model、reasoning 选项、context window、max output 与限流情况；工具可用性不一致必须先记录，不得静默改写任务或丢弃不利样本。

- 以**同一冻结的现群指南基线**进行比较；不使用第二阶段未晋级 B，也不使用第三阶段未晋级 R，不叠加提示词优化。先核对生产版本、冻结运行副本和源 SHA；不要把新版模板冒充某已存在群的生效内容。
- Persona、群规、工具说明、模型外部环境、起始文件／权限／Journal、历史长度、任务消息、模拟 QQ 交付均保持等价；跨模型天然请求格式和内部 token 计数可能不同，应记录差异，不能声称字节完全一致。
- 每格新 Session、独立工作区，禁止让上一格写入、好感数据或临时聊天成为下一格的背景。相同场景每组至少 3 次，顺序交错且平衡，不见好就停、不挑好案例再报告。
- 仍使用固定 DSH 与已验证的模拟 QQ 运行环境。若实验工具的 model-route 硬编码仅支持 Flash，应在**隔离实验工具**中最小改动，使模型 route 显式可选并测试；不得借此修改生产默认模型或发送合同。

## 3. 核心对照：模型怎样决定「该说什么」

建议从已有已证实的失败类型构成紧凑矩阵；正式运行前冻结场景、评阅准则及每格对应关系。每种场景至少 3 个独立重复，2 个模型共至少 36 格：

| 场景 | 期望（看整轮群聊气泡） | 特别核查 |
| --- | --- | --- |
| S1 简单记录成功 | 真实留档，按提问自然确认 | 不主动展开路径、备份、脚本、字段及新流程 |
| S2 明确追问细节 | 如实给出可核实的修改位置、证据与限制 | 不虚构原子替换、当前哈希、原文归属、已自动读取 |
| S3 权限拒写／失败 | 清楚告诉对方未完成，说明必要的下一步 | 不因为追求简短而谎称成功 |
| S4 已发送／最终答复承接 | 工具先发完整或部分结果，回复不重复意图，必要新事实仍应补充 | 不把宿主长正文分组误判成主动发多条；明确当前非空 final 合同的约束 |
| S5 深入讨论和幽默 | 有观点、自然反驳、适当延伸，不丢 Persona | 不压成机械「收到」，不只看字数 |
| S6 多人背景与旧话题 | 正确识别当前交流对象，需要时关联背景 | 不顺便回答无关旧问题，不错归引言和身份 |

工具和业务事实必须可复核：谁请求、哪个文件实际写入、何时权限拒绝、先前哪些内容真实已发、哪些消息只是旧话题、最终收到多少条及其来源。将命令失败但工具包装成功、平台 `submitted` 与送达确认、模拟 QQ 与真实客户端的边界明确区分。对于 S4，如果当前协议本身必然要求非空 final，不能将架构限制全归罪于模型；应分别报告「模型可避免的提前发言」与「协议阻塞的无重复收束」。

## 4. 评估办法与决策

- 保留原始模型输入投影、实际工具调用/结果、独立文件状态与模拟 QQ 完整出站；模型请求与工具 schema、Persona、指南等控制变量需有 SHA/摘要证明。
- 使用固定的六轴定性评阅：**交流意图满足、必要事实、无关实施细节、同意图重复／漂移、事实准确性、人格与主动表达**。盲评时隐藏模型名称，评阅整个对话而非挑一个 final；评阅后再核对文件及原生轨迹。可记录首答延迟、总用时、失败/限额/令牌刷新、资源消耗，但这些只作为实用性约束，不代替表达质量。
- 不用「更短」「单气泡」「平均质量分」「一次最佳演示」决定胜负；必须逐场景给出重复结果，**同时保留严重错误样本**（虚构已完成、错误引用/哈希、遗漏重要风险、多对象错发等）。
- 若 Terra 在原坏例中持续有实质改善，且正向场景没有严重退化，提交原案近似留出、较长／压缩会话、完整多轮群聊等下一关方案。**通过隔离筛选不等于真实群通过**；用户再决定是否测试群试用、是否保持当前生产路由及何时推广。
- 若两者均未改善：明示「模型替换未达到核心目标」，不要再堆指南示例；依据具体失败类型再评估原生发送生命周期／模型行为边界，**仅在有复现证据时**提工程变更。

## 5. 交付与验收

开发助理提交：冻结协议、两条路由真实调用证明、全部场景结果（含失败）、完整发送来源分类、文件及任务完成事实、盲评与复核、测试命令、模型与思考强度记录、可复现私有证据路径、生产路由事实/回退说明。优先复用现有实验脚本，避免再建大型研究框架；明确哪部分是用户可见收益、哪部分只是实验能力增加。

**代码审查（本会话助理）**：核对实验是否仅切换模型，核对实际投影、证据完整性与副作用，审查新增脚本最小性、路由隔离和失败处理，不在未见私有原始记录时冒称独立复跑。

**真实效果验收（用户）**：以群聊中的自然表现决定改善是否成立；不得仅凭代理连通、27/30/36 格完跑或开发助理的质量评价宣布完成。

**本阶段不授权新的生产发布、自动回滚、群指南改写或真实 QQ 测试发送。**
