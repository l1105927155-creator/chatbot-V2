# QQ 附件双向传输：实施契约（2026-10-18）

> 状态：需求与技术边界确认；**尚未实现或验收**。本文件不是代码完成证明。
> 依据：当前 Journal 仅保留媒体元数据，群聊 DSH 的 Bash 断网；NapCat OneBot 提供 get_image/get_group_file_url/get_private_file_url、upload_group_file/upload_private_file 等接口。必须在部署锁定版本中验证实际返回结构与路径可达性。

## 目标

用户在 QQ 发送 TXT/JPEG/PNG/PDF/ZIP/音视频及其他普通附件，Agent 能按需把**原始字节**导入当前授权工作区；也能按用户要求把工作区文件作为 QQ 原生附件发送到同一个来源会话。文本和二进制统一处理，不依赖文件扩展名猜测内容，不要求模型把二进制转为文本，也不解除群聊 Shell 的断网隔离。

“存储/读取文件”与“理解图片/音频等媒体内容”是独立能力；本阶段不承诺视觉或语音模型。

## 分工

- **AstrBot / OneBot 边界**：根据当前真实消息的 Journal 记录定位附件，调用已连接的 NapCat API 获取真实原始字节；负责 QQ 原生附件上传、发送回执和下载限制。
- **受信执行/文件传输层**：依据当前 turn 的真实 platform/bot/conversation/source 和执行域，将文件以流式、受限的方式复制到当前会话目录。群聊必须使用该群专属、已验证的 ext4 工作区；不得让一个运行在宿主的 MCP 进程通过任意字符串路径绕过沙箱隔离。Owner 私聊遵守主机当前 Linux 运行用户权限，仍以已核验身份为入口。
- **DSH**：通过 MCP 工具选择何时导入、列举、发送；Shell/文件工具处理工作区内已存在的字节。没有附件无需例行调用。
- **Journal**：继续存放消息事实和媒体元数据，不把大型媒体 Base64 复制进 Journal、模型提示词或工具回复；回执存操作状态、源消息/附件标识、大小与摘要，不泄露实际宿主路径或凭据。

## 建议 MCP 合同（最终命名以实际实现为准）

1. `qq_attachment_import(journal_id, attachment_index, destination_name?)`：仅允许读取**当前来源会话**可见且真实存在的入站附件；从 Journal 按有序媒体段验证类型与文件标识；返回相对于本执行域工作区的文件名、字节长度、SHA-256、媒体类型（若可验证）；不允许任意 URL 作为输入。
2. `qq_attachment_send(relative_path, display_name?)`：仅允许读取本会话工作区内由程序验证的常规文件，发送到**当前来源会话**（群→该群；Owner 私聊→该 Owner）；不接受任意目标群、任意用户 ID 或绝对宿主路径。返回提交与平台确认状态，不把“提交”冒充成功。
3. 文本文件仍可经原生 Shell/文件工具读取；图片/压缩包通过真实文件字节保留，不强迫模型逐字节编码。

## 必须先核实的底层事实

- 锁定 AstrBot/NapCat 版本中图片、群文件、私聊文件分别需要什么 file_id / busid / file 参数；回传的是可用 URL、NapCat 主机路径还是 AstrBot 当前进程可读路径。**不允许假设 NapCat 与 AstrBot 共用文件系统**。
- 如果需要 HTTP 抓取，固定其为受信 NapCat 文件来源，不让模型提供任意 URL；校验解析 IP、跳转、协议、长度及内容大小，避免 SSRF 和无界下载。按接入方式实现跨主机传输而不暴露安全沙箱网络。
- NapCat 上传的文件路径相对于哪个进程？跨主机时需要受控上传/转运能力，不能把 AstrBot 本机路径直接传给 NapCat 并假装成功。

## 安全与资源约束

- 输入仅为已存在 Journal 条目中的附件索引，且属于当前会话；不允许跨会话导入、重放他人的消息附件或下载任意外链。
- 目标为普通文件；对相对路径做规范化、目录 fd / no-follow 约束，拒绝路径遍历、符号链接、硬链接/设备节点、覆盖冲突和权限绕过。应先写私有临时文件、校验哈希与大小，再在同目录原子落盘；失败清理残留。
- 限制单文件尺寸、总字节、并发与下载耗时，执行前检查当前群卷可用空间；空文件、重名、损坏、下载中断、重定向、失败返回必须可区分。
- 群聊传输服务虽在宿主中运行，也只能写入**当前群卷**；不能通过 MCP 路径或文件 ID 把宿主、Owner、其他群数据导入/导出。保留当前 turn/token 的授权检查，不依赖 Prompt 自觉。
- QQ 文件发送成功与否按 NapCat/OneBot 实际回执记录，不应自动重放不确定上传；避免与 AstrBot 自动最终文本回复重复。

## 验收门

1. 同群两名普通成员分别发送 TXT/JPEG/ZIP，原字节 SHA-256 一致，可跨成员读写；下载内容不是扩展名伪装的文本。
2. 群成员请求回传文件，QQ 收到可正常打开的原生附件；文件大小/哈希一致；不得误发到其他群或 Owner 私聊。
3. Owner 私聊能从 QQ 导入并发回二进制文件，使用主机已授权目录；非 Owner 普通私聊不获得 Owner 主机能力。
4. 跨群 Journal ID、任意 URL、路径遍历、符号链接、跨群/宿主文件读取、超大文件、下载中断、失效 URL 等均拒绝，已写入的旧文件与新状态不被损坏。
5. 完成模拟 OneBot 回归、真正的 NapCat 文件上传/下载与真实 QQ 双向收发测试；验证真实路径和回执。不得把 MCP/代码静态检查当作 QQ 平台验收。

## 与当前实施关系

`astrbot-plugins/v2_journal/journal.py` 的 `normalize_segments` 有意只存元数据；`astrbot-plugins/v2_dsh_router/mcp_server.py` 目前只有会话历史、群信息和独立文本消息工具；群聊 Shell 断网。**这些现状解释了“TXT 可写而 QQ 图片不能导入”，不是 JPEG 本身的文件系统限制。** 本需求应由平台受信附件传输层补齐，而不是修改回复提示词、允许沙箱 curl 联网或直接开放宿主文件系统。
