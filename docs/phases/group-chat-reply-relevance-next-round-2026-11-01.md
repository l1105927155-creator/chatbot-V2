# 群聊回复相关性：下一轮研发目标与验收边界

日期：2026-11-01  
状态：**待开发助理执行；不代表整改完成或允许上线**。  
基于提交 [ee622cf](https://github.com/l1105927155-creator/chatbot-V2/commit/ee622cf0a1ac8fe050492d3b45ecf8cec5f6c2aa) 的审查。总需求与最终验收以 [群聊回复相关性整改方案](group-chat-reply-relevance-2026-11-01.md) 为准；第一轮取证与阴性对照见 [实施记录](../evaluations/group-chat-reply-relevance-2026-11-01.md)。

## 0. 本轮起点、目标与边界

**已由第一轮报告支持：** 2026-11-01 00:57 的问题轮次由模型主动产生三次 `qq_send_origin` 和一次 final；平台回执与 Journal 能逐条对应。工作区 AGENTS.md 在有效原生 system 中，虽然会话此前发生四次压缩，未见其因此消失。本次确有文件写入。未发现发送层自行制造额外三个气泡的证据。这些是**开发助理生产取证报告的结论**；原始私有证据尚未由本次审查者独立复跑，不应扩大为所有场景的保证。

**仍未解决：** 为什么模型在完成「记录违规」后，把文件路径、章节、备份和无关巡查讨论当成值得发给群友的信息？新原则 B 在第一轮「任务已经完成后的续接」中三次均未达到原案目标，还出现了「偏好文件每轮自动可见」的事实误报。留出讨论能展开反驳，仅支持未见统一退化为「收到」，不能证明其他个性场景通过。

**本轮目标**：验证模型是否能从交流目的出发决定该说什么，而非根据掌握多少实现细节决定该报告什么。**不追求绝对短答**；有必要的异常、追问、长讨论、幽默和有价值的主动延伸应保留。代码正确性由本会话审查助理验收；真实 QQ 群交流表现由用户验收。

**禁止作为默认方案：** 每轮字数／发送条数上限、按句硬拆、关键词删改、语义过滤器、第二个改写模型、无依据修改 Persona、强制每轮读取 `memory/preferences.md`、直接覆盖已初始化群指南。不要因为本轮目标带有「开发」二字就强行实现尚未证明有效的改动。

## 1. P0 — 从用户请求开始的完整任务 A/B（本轮最高优先级）

第一轮对照在 Shell 成功写入后的原生 seq 3164 续接。此时旧 AGENTS 内容仍存在于历史工具输出中，且任务内的操作、工具选择和临近上下文均已发生。它只能衡量**已有工作后的收尾**，不能替代「新原则贯穿整个任务」的验证。

### 要做什么

在**隔离模拟 QQ、独立沙箱和可恢复工作区**，使用同一模型 route、配置、Persona、共享规则、工具能力和初始事实，以相同请求从本轮第一步开始执行：

- A：当时现群原版 AGENTS；B：仅替换已审阅的「你的回复习惯」核心段落的候选版。没有其他提示、工具描述、发送协议或 Persona 变化。
- 分别测试：（1）简单「把这次违规记下来」；（2）「记下来，并告诉我怎么记的／给我能核实的依据」；（3）记录失败、权限不足或结果未知的情况。第三种通过**可控且真实语义的工具故障夹具**提供，不得把失败伪装成成功。
- 操作本身需按权限及任务语义执行，验证实际文件／任务状态；**只看聊天正文、忽略真正有没有写入，不算有效样本。**
- 一次模型生成不可代表稳定行为。采用预先固定的重复次数、交错运行顺序与盲评准则；保留全部失败和偏差，不见好就停、不事后更改分类。
- 分开记录「从请求开始应用 B」与「任务完成后才改 B」的影响。如需控制旧指南工具结果的竞争，另立一个独立变量，不同时变更请求、历史、Persona 或工具。

### 应回答的问题

1. B 是否会**根据请求对细节的需求**而改变结果表达，而不是无差别压缩？
2. B 是否改善原案例的冗余报告？若仍失败，输出具体的「工具后发送选择／正文内容」轨迹，而不是只写「模型不遵循」。
3. 在失败和未知结果时，是否仍能说明必要事实？是否虚构文件会自动加载、未来每轮必读、已经成功等承诺？
4. 如果 B 没有可重复的优势，明确结论「候选无可验证收益」，不要直接上线或继续堆砌禁令。

**P0 交付门槛**：能独立复现、明确控制的 A/B 对照 + 每轮真实输入投影、有效指南、工具结果、文件状态、模拟 QQ 气泡、回执与 Journal、最终终态及清理证明；数据可复核，未公开群消息/凭据。

## 2. P1 — 无关旧话题的主动延伸（单变量归因）

本案最后一条巡查错误建议有可追溯的历史群聊来源，并非凭空出现。但「能在 Journal 里看到」是否导致「把它顺便说出来」尚未证明。当前 `service.py::_prompt` 会提供近期 Journal 增量；不能为了减少插话简单删除全部群聊背景——Bot 需要理解多人交流。

### 对照设计

冻结同一最新唤醒消息、当前任务结果、Persona、模型、当前生效的指南、工具 schema 与其他消息，只改变最近 Journal 中**与当前请求无关、但容易引发模型主动回应的一段旧讨论**：

- 无旧讨论（对照）；
- 有与当前请求无关的旧讨论（干预）；
- 可选正控制：旧讨论确实存在紧急、需立即回应的实质信息，或对方明确要求连接两个话题，以防把「不主动延伸」误测成「不会发现重要信息」。

明确标注旧话题在 Journal 中的来源、是否 @ Bot、是否有人已回答、时间顺序、当前提问与其关系。不得把群成员发言冒充更高优先级指令，也不得删除和改写真实生产 Journal。优先以真实样本的**脱敏、冻结、隔离复制**构建夹具。

### 验收关注点

- 记录类当前任务不应因为出现旧巡查讨论就额外发送无关「顺便说一句」；
- 其他成员的确有重要信息、或者当前问话真正需要关联旧话题时，Bot **仍允许主动提醒或联系上下文**；
- 如模型只在某种旧讨论、某个 Persona 或某种先前回答示例下漂移，注明是条件相关的现象，不能无依据宣称「Journal 导致问题」。

**P1 交付门槛**：逐例说明被纳入的背景为何相关／无关；对照输入除了目标变量确实等价；测量的是**内容与回应意图**，不是字数、段落数或消息条数。

## 3. P2 — 已发送内容与 final 的职责（有证据再动）

第一轮已证实多条来自模型主动 send，但没有发现宿主重复投递；历史 [reply-root-causes](../evaluations/reply-root-causes-2026-10-29.md) 的 G/D 提示对齐也没有稳定收益。因此 **P2 是隔离验证的备选，不是默认必须重构的模块**。

仅当 P0/P1 显示明显的多次公开发送、工作汇报进度化或 final 语义复述时，分别对照以下候选：

- 明确 `qq_send_origin` 发送的是**群友已经能看到的内容**，不是不可见的执行日志或内部草稿；
- 完成任务的自然确认、真正的独立新消息、必要等候提示与最终正文的职责如何区分；
- 工具已经发过结果后，final 不再重复同一**交流意图**；允许补充尚未告诉对方、且实质重要的信息；
- 如提案允许「仅工具发送、没有最终文字」，必须先独立解决当前非空 final 合同、回执未知、失败兜底和防重放；**不得直接以空 final 视为已完成**。

多对象回复、@ 与引用、任务失败、真实长内容和定时轮次必须保持可用。优先改高层说明／工具描述并对照，除非已有工程缺陷证据，否则不触碰发送管线。不要把连续三条消息误判成「任何超过一条的回复都错误」。

**P2 交付门槛**：证实修改的是哪个决策错误；在受控基线中带来可重复收益且不丢事实；若没有，停止修改并记录负结果。

## 4. 诊断工具的两项准确性补强（小范围独立处理）

上一轮代码审查对新增 `scripts/inspect-reply-relevance.py` 提出两个问题，需先复现、评估影响，再以最小修改修正；不得把这两项当作表达质量修复。

1. **`build_report` 的 `status=matched` 语义**：目前整体 status 主要由入站 Journal 与 native prompt 匹配决定，可能在 native turn 不完整、出站 attempt 未回执时仍是 `matched`。明确该状态是「入站身份匹配」还是「整轮证据完整」；建议分别暴露入站、原生、发送和回执状态，不能让消费者误把来源吻合当成完整平台投递确认。
2. **`native_turn_evidence` 的 `final_message_seq`**：取最后一条 assistant/message 不能自动断定它含真实最终文字。区分有正文的最终回复、仅工具调用、空正文、轮次中止及无终态；保持与上游实际 terminal receipt 的语义一致。

补齐**无模型确定性测试**：完整／缺失回执、空 final、工具调用型 assistant 末条、无 turn/end、跨会话 ID 混淆等。保留隐私与只读约束，现有 native 审计、SQL/Journal 身份匹配规则不得退化。若测试说明既有实际报告未受影响，明确记录，不制造本案取证无效的新结论。

## 5. 实施顺序与停止条件

1. 先补取证工具状态语义回归（如确认问题），固定当前 main、部署代码、现群指南/Persona、模型 route 和夹具 SHA。
2. 优先运行 **P0 从头开始的完整任务对照**；分别判断必要信息保留与无关汇报减少。对照阴性也要报告。
3. 再运行 **P1 无关旧话题对照**。P0/P1 若已经定位可改的最小原因，先提交证据和候选差异，**不要自动进入大范围重构**。
4. 只有观察结果需要时再评估 P2。涉及改变现有空 final、工具发送协议或用户可见行为的修改需独立审查后才能推广。
5. 对多个候选，不得一次改变模型、Persona、工具协议、Journal 注入和指南。每个单变量结果独立归因；后续组合试验须在单项结果成立后进行。
6. 一律使用隔离环境做自动化测试。生产群不自动同步 AGENTS、不修改人格/记忆、不重置会话、不主动投放测试消息。**候选实现／实验通过 != 用户授权上线。**

遇到模型通道不可用、夹具不完整、原生输入无法验证或对照失去变量控制时，停止宣称因果结论；提交当前可验证的部分及阻塞项。不要以虚构回执、模拟模型生成替代真实模型实验。

## 6. 交付与两级验收

### 开发助理必须交付

- 排查结论矩阵：已证实、被排除、未证实；每项指向源码、原生记录和对照结果；
- 拟改／已改的文件清单与最小 diff；不改的机制及理由；风险、回退办法与生产影响范围；
- P0 和 P1 的冻结协议、A/B 每格结果、有效请求投影与模拟 QQ 真实气泡、已完成/失败/未知事实、模型与工具版本、完整性和清理证明；
- 诊断脚本两项状态语义的测试与结论；相关原有测试运行命令和通过/失败/跳过清单；
- 对九类原需求验收场景的覆盖情况：覆盖了哪些、仍需哪类验证，不能把本轮小样本冒充全部验收。

### 审查助理负责代码验收

复核各修改是否有证据、两脚本状态语义是否正确、模型输入与发送链记录能否自洽、原有权限／Journal／记忆／好感／合并转发／长内容／多对象行为有无退化。**未取得原始私有实验证据时，区分「报告内容已核对」与「独立复跑通过」。**

### 用户负责真实群聊效果验收

评判 Bot 能否按交流意图选择内容：记录后自然确认，追问时详细说明，失败不虚构结果，闲聊与讨论仍有个性，可合理反驳和主动延伸，不把无关执行流水和旧话题惯性发送出来。**回复变短并不单独等于合格**。用户未实际验收前，维持「表达整改未完成」。

## 7. 下一轮完成的定义

下一轮完成不要求立刻声称「机器人回复问题已根治」，而要求**比第一轮更明确地划分成因与可行方案**：

- P0、P1 至少得到可信的正／负对照结果，能回答「新规则在任务开始前生效是否改善」以及「无关群聊背景是否导致无关主动延伸」；
- 诊断工具的两个精度问题已修复或有充分证据说明无需修复；
- P2 要么有证据支持具体方案、通过针对性契约测试，要么明确作为未采用项留档；
- 代码变化最小，保留正常表达的自由度，不部署未经用户允许的生产行为改动；
- 交付足以供审查助理再次审查的 commit、报告、测试与风险说明。
