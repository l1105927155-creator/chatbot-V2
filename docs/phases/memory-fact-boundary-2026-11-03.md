# 记忆写入：客观事实与主观理解

用户明确核心规则：**客观事实需验证，主观理解随意发挥。** 本轮改进记忆生成的职责与可见输入，保留现有来源编号、存储、原子提交和失败范围合同。

## 已核对的问题

真实Journal42438是邀请大家观看演示视频并投票；42439是合并转发。原整理输入没有展开转发，也没有保留转发存在和本次内容不可见的状态。模型在`content`中写成“发演示视频”，而对应claim仍准确表达邀请。这证明引用核验并不等于摘要含义得到支持；不能据此断言视频实际上没有发送。

原指南笼统允许“误解”，没有限定客观部分的边界，也没有要求`content`和`claims.text`受同一事实规则约束。原样本另有跨日摘要日期错误，消息时间本身正确。

## 实现

- 生成指南以用户规则开头，要求正文和claims同时核对主体、动作、时间、完成状态；群友和Bot自述保留归属，主观理解自由表达，其客观前提仍须有来源。旧摘要也回到来源核对。
- `evidence.py`为媒体及forward段提供可编号的结构化存在事实，并说明本次内容未提供。不暴露引用ID、summary、URL或嵌套内容，不推断过去是否查看或是否发过视频，不自动展开转发。
- `backend.py`在生成及精确来源绑定之后，增加独立事实核对。每条记忆分别调用同一原生模型；输入保留本批完整原文、主体/时间/宿主观察、当前记忆引用的历史Journal行及待核对草稿，允许纠正草稿错引。历史摘要、claims.text和草稿都不作为独立事实证据。
- `fact_review.py`按原生容量和实际协议字节构造完整请求；每条记忆独立，避免多条核对时相互合并或串写。局部整数引用由宿主重新绑定；兼容已验证但不对齐固定分片的历史引句。保留本批无文字转发/媒体观察，历史行只追加当前记忆的来源，不把其他记忆的历史上下文重复塞入。核对输入用message_ref字符串定位消息，evidence_id是唯一可引用整数，避免Journal编号混入引用。
- 核对保留原ID、成员、权重、状态，只修正正文与claims的客观前提、归属和确定性，保留主观表达。结构/来源校验失败时不写草稿；全部核对成功后，再复查全部依赖的Journal投影（包括时间和媒体观察）、人格与路由，执行一次CAS提交记忆和游标。
- 全流程沿用取消、Owner编辑/停用、失败范围和不自动重试合同；新旧输出协议都经过核对。用量计入生成及核对的实际调用，缺失测量保持未知。私有诊断区分生成、核对、重绑及上下文变化，并指向实际失败的核对包。
- 既有quote来源与SQL表结构保持；claims JSON增加严格互斥的observation来源，绑定真实Journal、主体、方向及段位置/媒体类型。宿主观察不伪造quote，note及本次not_provided不作为永久事实保存；重读、修订历史与导出兼容。管理页区分原文与宿主存在来源。不增加置信度、事实分类表、逐条人工审批或通用事实判定平台。核对后新增来源从最终claims派生，既有历史由Store保留，避免重新引入200条任意引用上限。

## 能力边界

精确引句校验只能证明原文及身份，独立语义核对用于纠正客观前提、时间和动作状态；二者不能证明任意外部事实。缺少可见内容或实际执行记录时保留原说法、推测或未知，不反向断言没有发生。主观印象不受客观摘抄限制。

每条记忆多一次真实模型调用；单条记忆及其完整来源/本批宿主观察仍可能超过所选模型的原生容量或保守字节预算，此时明确报错并保留游标，不截断引用或无限重试。当前不声称任何未来摘要都会准确，也不把旧版3881条全量运行的结果当作新核对流程的验收。
