## 1. 唯一目标与已定业务边界

**唯一目标：Bot 的聊天表达质量取得稳定、可验证的改善。** 不以字数更短、气泡更少、语气词更多、工具调用成功作为效果达标的替代指标。

用户已明确：

1. **工具型能力与聊天型表达并存。** 复杂任务可以在后台执行，但群里默认只交代对方需要的结果。普通记录/修改完成可自然回复“记下了”“改好了”；不主动报告 `memory/preferences.md`、备份名、修改清单、技术过程、逐条日志或“顺便说一句”的无关建议。若对方明确询问依据、实现、进度、比较、原理，或出现重要失败/不确定结果，则如实且充分展开。**专业任务≠默认专业报告；专业讨论也不必强制缩短。**
2. **交流形式不设固定配额。** 自然、相对短促的 QQ 群聊表达；允许一句就结束，允许自然地连发，不按标点逐句拆，也不为了控制条数将回答、吐槽和追问堆成一条过于工整的长气泡。不凑气泡、不重复同一语义、不套固定人格收尾。对话人格应充分体现，但不需要每轮演一套“嘴硬—让步—哼”的动作。
3. **@ 和引用用于消除多人交流歧义。** 应在本轮合适的消息上明确特定对象，**不固定第一条**。例如可以先发“我的天！”，随后“@B 你刚才说的是真的吗？”；对同一对象、同一段交流无须反复 @；切换对象或引用来源才重新明确。
4. **交付载体平等。** 普通气泡、QQ 原生合并转发、Markdown 文件和一张合适的 meme，**各自都可以单独构成完整公开回复**，不强制附带“文件发了”“好了”或新的正文。也允许用户明确指定其偏好的载体。
5. **Persona 允许持续优化且不能弱化到无个性。** 当前是傲娇角色，但应避免教科书式固定台词、频繁贬低简单提问、机械收尾。适当的“呢、嘛、哦、呀、啦、吧、啊”等语气词体现语用和情绪，不设数量/比例要求，也不强制每句使用。

## 2. 已核实代码事实与假设边界

| 事项 | 当前仓库事实 | 不允许的推断 |
| --- | --- | --- |
| 普通气泡 | `qq_send_origin` 可独立发送 QQ 消息；final 是另一条完整消息，`qq_prepare_reply` 只设置 final 的原生 @/引用。见 `mcp_server.py`、`messaging.py` | “模型没有调用 `qq_send_origin`”不能直接证明程序不支持多气泡 |
| final | `dsh_client.py` 要求 `end_turn` 且非空白 final；`service.py` 会验证并公开发送 final | 不能在提示词里要求“空 final”而假装目前已支持纯工具结束 |
| 文件与转发 | `qq_file_send` 发送文件；`qq_send_forward` 发送原生合并转发。Markdown 是**文件交付**，非普通 QQ 正文的 Markdown 卡片渲染 | 不是所有信息多的回复都应转换成附件或合并转发 |
| 交付回执 | 工具返回 `submitted: true, platform_confirmed: false`，真实平台/Journaling 后续另有观察路径 | 不能把提交当作 QQ 客户端确认，或在未知结果下盲目补发 |
| 已有实验 | 2026-11-01 第三阶段结果选择候选 R 未取得稳定收益，S 受现有非空 final 合同阻碍而停止；旧工具职责提醒实验亦未稳定胜出 | 不能重复同一条规则试验后宣称“改进已获证实” |

**需要实地核对**：当前 `main` 不必等于实际部署；开发前须读取现有部署版本、群实际 AGENTS/Persona（不是模板文件）、DSH pinned 版本、发送工具 schema、协议终态与 QQ 出站路径。私人会话导出仅作为现象样本，不能代替生产代码事实。

## 3. 决策分层：先“说什么”，再“怎么说”，最后“怎样送达”

### 3.1 交流目的与内容选择

| 场景 | 应公开的内容 | 默认不应公开 |
| --- | --- | --- |
| 简单执行/记录成功 | 简短确认或关键业务结果 | 路径、备份、调用过程、测试清单、额外建议 |
| 简单事实问答 | 正确答案及必要的补充 | 无关新闻和资料汇报、冗余日期解释 |
| 闲聊/情绪互动 | 自然接话、人格化反应；允许真实追问 | 套路式“哼”尾句、重述刚说过的话 |
| 专业讨论、清晰的求证 | 足够的推理依据、比较、限制 | 没有必要的执行日志 |
| 明确要求操作细节 | 真实步骤、文件、证据与状态 | 编造已完成操作、编造核验 |
| 失败或回执不确定 | 如实说明未完成、未知及必要影响 | 用“收到/好了”掩盖状态 |
| 资料清单/正式报告 | 便于逐项阅读或保存的完整成果 | 在群里刷大量细碎气泡 |

不要建立“闲聊模式/专业模式”的硬关键词分流器。由实际交流目的决定内容详略；“专业任务”可以只回“改好了”，而成员主动要求讨论技术问题时可以讲透。

### 3.2 语言与 Persona

- 采用**A 类内容克制**：先选真正要说的内容，不为表现角色或工具能力制造额外内容；仍保留即兴情绪、吐槽、嘴硬和自然让步。
- 允许自然短句与情绪语气词，但不能硬性要求 `1–15` 字、`1–2` 条、每句单独气泡或“每句加一个呢/嘛”。
- “按自然对话节拍分条”是可用的表达手段，**不是必须经历“回答—反应—调侃”的固定流程**。若一条就自然，直接结束；若短暂停顿或接话自然，也允许另发。
- Persona 重点是性格动机、与不同熟悉程度的人互动、正负情绪与语言倾向；减少固定台词模板。中文语气词的出现须在同样任务与模型配置下评阅**是否恰当**，不是统计出现率越高越好。
- AGENTS 负责交流目的、群规和交付约定；Persona 负责人格/自然语言；MCP 描述负责参数与工具效应。不要让三处反复书写含义相近却相互竞争的命令。

### 3.3 输出载体选择

| 载体 | 适用条件 | 注意 |
| --- | --- | --- |
| 普通 QQ 气泡 | 日常对话、情绪回应、简短问答、专业问题的简短直接答复 | 自然分条，但不逐句机械切分 |
| QQ 合并转发 | 多项独立建议、比较、资料等需要分项浏览，普通气泡会明显造成刷屏 | 不当作“几句闲话”的收纳箱 |
| Markdown 文件 | 需要保存、复制、长期阅读的报告、教程、长方案 | 允许文件本身即为交付，不强制追加总结 |
| meme | 适合以表情回应的语境 | 允许独立作为回复，不强制配文字 |

依用户要求与可读性选载体，**不按字符数跨阈值机械路由**。不新增二次 LLM 改写器、自动“句号拆气泡”器或复杂载体路由层。

## 4. 开发实施路线（必须分开验证）

### P0：核实生产合同与建立新的可复核基线

1. 对齐 `main`、实际部署代码、固定 DSH、当前真实群工作区 AGENTS/Persona 与工具 schema，记录 SHA；真实群不改动。
2. 复用仓库既有沙箱与 Journal/OneBot 出站收集，不重建实验框架；用匿名样本覆盖：简单倒计时、情绪反馈、嘴硬与承认、写入确认、追问实现、失败/未知回执、多人先感叹后 @、资料/文件/meme 交付。
3. 同时采集模型实际看到的指南、原生请求、`qq_send_origin` / `qq_prepare_reply`、final、宿主分组、最终 QQ 气泡与媒体。**将模型主动分条、宿主分组、单条内部换行分开统计**。
4. 保留先前 R 和工具提醒实验的阴性结果；新候选需说明与旧候选的本质差异，禁止循环同一提示词实验。

### P1：先验证“内容与 Persona”，不先重构发送架构

- 在隔离环境只替换回复策略相关的 AGENTS 段落，保持 Persona、模型、工具定义与发送代码不变；对照基线。
- 另起一组**只替换 Persona**：去掉强模板台词，保留鲜明傲娇角色、自然中文口语（适度语气词）、真诚关怀和自主判断；AGENTS 及其他条件不变。
- 单项有效后再组合检验，不能一次替换两份指南然后倒推原因；适度引入长历史/会话重置对照，避免把一次漂亮答复当作稳定收益。
- 检查简单完成时不公开内部流水；被追问时能详细作答；长讨论自然展开；不能单纯将 Bot 压成冷冰冰的“收到”。
- 如果没有可重复改善，报告阴性结论并停下，不继续添加多条文本禁令。

### P2：独立评估并实现“纯工具公开交付即可完成”的合同

该需求**已获用户业务认可**，但具体工程方案待技术评估。不能把它和 P1 的聊天风格改善混为一项收益。

- 在当前 `end_turn` 非空 final 合同下，先检查 DSH/ACP 及 V2 adapter 的可行接入点，确认怎样**显式声明本轮已完成公开回复**而不伪造文字 final。
- 推荐研究每轮独立的明确完成标记/交付收据：只有本轮目标会话内**明确声明该次已是完整公开交付**且提交成立时，才允许不再公开 final；中间工具消息、单纯等待提示、部分文字不算完成。
- `submitted` 不等于平台确认送达；未知/失败不盲重发，不丢掉审计状态。取消、重置、定时轮次、跨对象交流、最终正文仍有必要的场景必须兼容。
- **不要**靠“嗯”“搞定了”、魔法字符串、空格 final 或随意吞掉 final 来绕合同；若上游不支持空终态，可仅在 V2 显式可信完成态中评估“私有终态不公开投递”的最小适配，记录其对 DSH 历史和后续回合的影响。
- 文件、转发、meme 和普通工具发送都应独立回归：成功、拒绝、未知回执、重复风险、部分发送、取消、跨群权限和 Journal 关联。
- 若无法可靠处理原生终态，停止在技术评估并报告不可行条件，不修改生产基础收发。

### P3：仅在证据充分时评估普通文字的一次规划/统一发送

此前 Session 存在“工具提前发送 + final 重复同义”“单 final 内 `\n\n` 换行却没分气泡”的现象。当前 `qq_send_origin → final` 已可实现自然多气泡；**尚未证明工具调用成本是单气泡偏好的根因**。

- 先用不改程序的对照确认：同一任务、同一指南及 Persona 下，模型为何选择一次 final 或显式 send，以及不同发送路径是否与内容选择、语义重复有关。
- 仅当证据显示现有输出机制系统性阻碍自然表达，才设计“模型一次规划若干公开消息、宿主逐条投递”候选；保留原生 @/引用、重置与失败回执，验证与现有工具的兼容。**不预先承诺实施**。
- 不根据句号、空行或字数进行宿主强制分条；否则又回到机械回复。

### P4：真实群受控试用与用户验收

取得可信沙箱改善、完整合同测试和可回滚 diff 后，再由用户批准测试群上线。不要动生产模型 route（生产 DS Flash、Terra 作为单独备选比较），不私自改全群自定义工作区、历史与 Persona。最终以真实聊天体验验收，不以测试脚本完成宣称项目已达标。

## 5. 验收矩阵与硬性退化条件

| 案例 | 预期 |
| --- | --- |
| “距离春节还有多久” | 准确直接，不附无关放假汇报；短句可一条也可自然连发；无重复解释 |
| “宝宝你语气好伤人” | 有性格、有真实情绪变化，不机械反复认错或凑“就这一回” |
| “把这条记下来” | 确实持久化后自然确认；不报路径/备份/改动流水/顺便建议 |
| “记在哪？怎么确认？” | 提供真实文件位置、方式及证据，不为了简短丢失必要信息 |
| 权限拒写或回执未知 | 如实说明，不能谎称成功/自动盲重发 |
| “我的天！” → “@B 你刚才说的是真的吗？” | 允许 @ 出现在后续气泡；同一对象不重复 @ |
| 多对象 A/B 分别说话 | 各自正确提及/引用，不误投 |
| 多项独立资料 | 适当用合并转发，非刷屏；简短专业解答仍可直接气泡 |
| 正式长报告/文件 | 文件即交付，不出现被迫的额外 final |
| meme 直接回应 | meme 即完成，可不补没价值的文字 |
| 已发前段 + final 仍有新内容 | 保留必要最后消息，不能因“已有发送”而吞掉 |
| 较长/压缩上下文 | 指南实际注入与行为留痕，不发生模式漂移及重复内容明显增长 |

**分别测量**：必要任务完成/事实准确、无关执行细节、语义重复、人格自然、语气词恰当性、真实 QQ 气泡/载体、无效额外发送、重复 @、工具提交与交付状态。每格多次独立重复并交错顺序；单样本只作为诊断，不能宣称因果或稳定改善。

**阻止晋级的严重错误**：虚构完成、真实失败被隐藏、重要异常被吞、重复/错发目标群、跨会话引用、未知回执自动补发、伪造平台确认、损坏历史/Journaling/取消重置合同。

## 6. 交付与暂停条件

开发助理应分阶段提交：

1. 实际部署/代码合同对照、原始基线证据及本次候选与旧阴性方案差异；
2. P1 两项单变量评估、组合测试与异常案例；只有正向证据才给出待部署的最小指南/Persona diff；
3. P2 原生协议可行性分析，能做则提交最小代码 diff、确定性回归、独立发送/回执链证据与回退；不能做则明确阻塞，不制造伪交付；
4. P3 只有在证据要求时提出新架构，不将“统一分条”写成已确定需求；
5. 对用户说明**实际变好了什么、退步了什么、尚未证明什么**；在用户明确同意后才部署测试群并进行真实效果验收。

禁止以“文档提交成功、工具验收通过、平均气泡数下降或 Persona 更活泼”代替核心目标完成。
